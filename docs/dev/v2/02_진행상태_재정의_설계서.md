## 1. 배경 — 현행(수동 journey) vs PDF(품목별 완료 + 게이팅), v1 비연동 원칙의 D2 절충

### 1.1 현행 journey의 성격

v1 G-11(`docs/dev/v1/05_업무흐름_갭_개발설계서.md` §3.2)은 journey를 **"사람이 관리하는 표시 레이어"**로 정의했다. 핵심 원칙 3가지:

1. 시스템 계산 상태(`order_items.status` 등)를 **대체하거나 자동 연동하지 않는다** — 이중관리 불일치 차단.
2. 단계 전진은 **전적으로 수동**. 시스템 상태와 어긋나면 화면에 **힌트만** 띄운다(강제·자동 전진 없음).
3. 단위는 **거래(주문) 1건**.

현행 `changeStage`(`backend/src/modules/journeys/journeys.service.ts:260`)는 이 원칙대로 구현되어 있다: 낙관적 잠금(`:273`), 전진 건너뛰기 허용·후진 사유필수(`:295`), 이벤트 이력 + 연락 제안(`:347`). **단, 어떤 단계로도 담당자가 바로 넘길 수 있다** — 완료를 가로막는 조건이 전혀 없다.

### 1.2 PDF가 요구하는 성격

PDF 1·2페이지 "완료 상태 체크 조건과 완료 버튼" 열은 **모든 실무 단계**에 동일한 2줄 규칙을 반복한다:

> - 상태완료 체크: **전체 품목 …상태 완료 여부**
> - 완료 버튼 조건: **상태 완료시 활성화**

즉 현행에 없던 두 개념이 추가된다.

| 개념 | 현행 | PDF v2 |
|---|---|---|
| **품목별 완료** | 없음(단계는 주문 통짜 1개 상태) | 각 단계에서 대상 **품목 하나하나**에 수동 완료 버튼 |
| **완료버튼 게이팅** | 없음(항상 아무 단계로나 전진 가능) | 대상 **전 품목이 완료되기 전 [전체 완료] 비활성**, 전 품목 완료 시 활성화 |

### 1.3 D2 절충 — "게이팅만 집계, 전진은 여전히 수동"

v1의 "자동 연동 안 함" 원칙과 PDF의 "품목 집계로 완료 판정"은 정면으로 부딪히는 것처럼 보인다. **마스터 D2**가 이를 정확히 절충한다.

- ✅ **완화하는 것**: journey 단계 전진(완료)의 **[전체 완료] 버튼 활성화 조건**을 품목별 완료 집계로 계산한다.
- ✅ **그대로 두는 것**: **자동 전진은 하지 않는다**. 게이팅이 열려도, 활성화된 버튼을 **담당자가 눌러야** 완료된다. 후진 사유필수·건너뛰기 규칙도 유지.
- ⚠️ **여전히 지키는 v1 원칙**: 품목별 완료는 **production 상태머신을 자동 추종하지 않는다**. 제작상태(BASTING_RECEIVED 등)는 게이팅의 **힌트/프리필 근거**로만 쓰고, journey의 "품목별 완료"는 **담당자가 누른 별도의 수동 확정**으로 저장한다(§3 권장안). 이로써 "이중관리로 인한 롤백 문제"를 피하면서도 PDF의 게이팅 요건을 만족한다.

정리하면, **집계는 하되 그 집계의 원천을 production 상태가 아니라 "담당자가 누른 품목별 완료"로 둔다.** 이것이 v1 원칙과 D2를 동시에 만족시키는 유일한 지점이다.

## 3. 품목별 단계 완료 추적 모델 (대안 비교 → 권장안)

### 3.1 요구사항 재확인

각 실무 단계에서 "대상 품목별 완료"를 저장해야 한다. 저장 위치가 곧 §4 게이팅 계산의 원천이 된다.

### 3.2 대안 (a) — 기존 production/rental/repair 상태 이벤트를 완료 근거로 매핑

단계별로 "어떤 item status = 완료"인지 정의하고, `computeAggregateStatus`류로 집계.

| journey 단계 | 완료로 볼 상태(가정) | 원천 |
|---|---|---|
| STYLE_CONSULTING | option_selection_session.status='CONFIRMED' | options |
| ORDER_REQUESTED | OrderItem.status ≥ PRODUCTION_REQUESTED | production-status.ts |
| BASTING_RECEIVED | ≥ BASTING_RECEIVED | production |
| FITTING_DONE | ≥ FITTING_COMPLETED | production |
| PRODUCT_RECEIVED | = RECEIVED | production(집계) |
| RELEASED | = RELEASED | production(집계) |
| RENTAL_* | RentalAllocation 상태 | rentals |
| REPAIR_* | RepairRequest.status | repairs |

- 장점: 신규 테이블 없음. 단일 출처.
- 단점(치명적):
  1. **원천이 트랙마다 제각각**(production/options/rentals/repairs) — 통일 집계 불가, 트랙별 특수 코드 난립.
  2. **STYLE_CONSULTING·RENTAL 단계는 production 상태 자체가 없다**(렌탈은 제작 이벤트가 없음).
  3. **v1 비연동 원칙 위반**: production 상태를 journey 완료로 직접 연동 → 롤백·이중관리 문제 재발(D2가 명시적으로 피하려는 지점).
  4. PDF는 "**품목별 수동 완료 버튼**"을 요구한다. 자동 파생 상태는 "담당자가 눌렀다"는 사실을 표현하지 못한다(가봉 입고 상태여도 담당자가 아직 확인 안 했을 수 있음).

### 3.3 대안 (b) — journey 단계별 품목완료 전용 테이블 신설 ★ 권장

담당자가 누른 "품목별 완료"를 **전용 테이블에 명시 기록**. production 상태는 이 테이블과 **분리**하되, 화면 프리필/힌트로만 참조.

```prisma
/**
 * 진행 단계별 "품목별 완료" 기록 (v2 D2).
 * 존재 = 그 단계에서 해당 품목이 담당자에 의해 완료 처리됨.
 * production/rental/repair 상태와 자동 연동하지 않는다(힌트만). 이것이 v1 비연동 원칙과 D2 게이팅을 동시에 만족시키는 지점.
 */
model JourneyStageItemCompletion {
  id          String    @id @db.Uuid
  journeyId   String    @map("journey_id") @db.Uuid
  stageCode   String    @map("stage_code") @db.VarChar(30)
  /** ORDER_ITEM | REPAIR_ITEM — 트랙에 따라 대상이 다르다(다형 참조) */
  targetType  String    @map("target_type") @db.VarChar(20)
  targetId    String    @map("target_id") @db.Uuid
  completedAt DateTime  @map("completed_at") @db.Timestamptz(6)
  completedBy String    @map("completed_by") @db.Uuid
  notes       String?   @map("notes")
  /** 완료 취소(되돌리기) 시 채운다 — 물리삭제 금지(구현표준 1.7). 집계는 revokedAt IS NULL만 센다 */
  revokedAt   DateTime? @map("revoked_at") @db.Timestamptz(6)
  createdAt   DateTime  @default(now()) @map("created_at") @db.Timestamptz(6)

  journey         CustomerJourney @relation(fields: [journeyId], references: [id])
  completedByUser User            @relation("JourneyItemCompletionActor", fields: [completedBy], references: [id])

  @@unique([journeyId, stageCode, targetType, targetId])
  @@index([journeyId, stageCode])
  @@map("journey_stage_item_completions")
}
```

- **다형 참조**(`targetType`+`targetId`)로 CUSTOM/RENTAL(=`order_items`)과 REPAIR(=`repair_requests`)를 한 테이블에서 흡수. FK를 걸지 않는 대신 서비스에서 존재검증(구현표준상 다형 참조는 앱 검증).
- 완료 취소는 `revokedAt` 소프트 처리 → 물리삭제 금지 준수, 게이팅 재계산 가능.
- unique로 같은 (진행·단계·품목) 중복 완료 방지 = 멱등.

**권장: (b).** 이유:
1. PDF의 "**수동 완료 버튼**" 의미를 그대로 표현(누가·언제 완료했는지 명시).
2. 3개 트랙(제작/렌탈/수선)의 이질적 원천을 **단일 집계식**으로 통일(§4).
3. v1 비연동 원칙 유지 — production 상태는 **힌트**로만 쓰고 journey 완료와 분리.
4. 자동 전진 없음(D2) — 테이블은 게이팅 활성화 근거일 뿐, 전진은 여전히 `changeStage` 수동.

**production 상태와의 접점(힌트, 자동연동 아님)**: §4 `GET .../items` 응답에 각 품목의 `productionHint`(예: "이미 가봉입고 상태")를 함께 내려, 화면이 완료 버튼 옆에 회색 배지로 표시하거나 "일괄 완료 제안"을 띄운다. 힌트는 **읽기 전용**이며 완료를 자동 생성하지 않는다.

**힌트의 원천은 대상 유형에 따라 다르다.** `productionHint.status`는 `ORDER_ITEM`이면 제작 상태(`order_items.status`), `REPAIR_ITEM`이면 수선 상태(`repair_requests.status`, 통합설계서 §12.1 6단계)다. 화면은 대상 유형에 맞는 라벨 맵으로 표시한다(`JourneyCard.statusHint`) — 코드값을 그대로 노출하거나 수선 상태를 "제작 상태"로 부르지 않는다.

**REPAIR 트랙의 도달 강조(프리필).** 수선은 수선 화면(6단계 상태)과 진행 카드(4단계 품목 완료) 두 곳에 각각 입력해야 한다. 수선 상태가 이미 그 단계를 지났는데 품목 완료가 비어 있으면 담당자가 누락한 것이므로, 힌트 배지를 강조색으로 바꾸고 "완료를 눌러 진행에도 기록하세요"를 안내한다(`repairStageReached`). 대응은 아래와 같고, **자동 완료는 여전히 하지 않는다**.

| REPAIR 진행 단계 | 도달로 보는 수선 상태(이상) |
|---|---|
| `REPAIR_REQUESTED` | `REQUESTED`(수선 요청) |
| `REPAIR_CHECKED_IN` | `RETURNED_TO_SHOP`(수선 입고) |
| `REPAIR_RELEASED` | `RELEASED`(출고 완료) |

> `CANCELLED`는 6단계 흐름 밖이므로 어떤 단계에도 도달로 보지 않는다.

### 4.2 게이팅 계산 함수

```ts
// journeys/journey-gating.ts (신규)

export interface GatingResult {
  stageCode: string;
  mode: 'AUTO' | 'GATED';
  targetCount: number;      // 대상 품목 수
  completedCount: number;   // revokedAt IS NULL 완료 수
  canComplete: boolean;     // [전체 완료] 활성 여부
}

/**
 * 단계 [전체 완료] 활성 판정 (PDF "완료 버튼 조건: 상태 완료시 활성화").
 * - AUTO 단계: 버튼 없음(canComplete=false, 별도 훅으로 완료)
 * - GATED 단계: 대상 품목이 1개 이상이고, 전 품목이 완료되어야 활성
 */
export function computeGating(
  mode: 'AUTO' | 'GATED',
  targetIds: string[],
  completions: { targetId: string; revokedAt: Date | null }[],
): GatingResult {
  const targetSet = new Set(targetIds);
  const completed = new Set(
    completions.filter((c) => c.revokedAt === null && targetSet.has(c.targetId)).map((c) => c.targetId),
  );
  const targetCount = targetSet.size;
  const completedCount = completed.size;
  return {
    stageCode: '',
    mode,
    targetCount,
    completedCount,
    // 전 품목 완료 = "상태 완료" (대상 0건이면 비활성 — 완료할 게 없음)
    canComplete: mode === 'GATED' && targetCount > 0 && completedCount === targetCount,
  };
}
```

- **완료 판정 기준**: `JourneyStageItemCompletion` 존재(revokedAt=null) = 완료. production 상태 무관(D2 절충 §1.3).
- **대상 0건 처리**: 대상 품목이 없으면 게이팅 비활성(전진할 실무가 없음). 실무상 발생 시 §10 미결로 관리(예외 허용 여부).

### 4.3 판정 흐름 (한 단계 라이프사이클)

```
[단계 진입] currentStage = STYLE_CONSULTING
   ↓ 담당자가 품목마다 [완료] 클릭 → JourneyStageItemCompletion upsert(revokedAt=null)
   ↓ 매 클릭마다 computeGating 재계산 → 프런트가 [전체 완료] 활성/비활성 토글
[전 품목 완료] canComplete=true → [전체 완료] 활성
   ↓ 담당자가 [전체 완료] 클릭 (자동 아님)
[changeStage] 서버가 게이팅 재검증(이중적용) → 다음 단계로 event 생성
```

## 5. 단계 전진 흐름 — 게이팅 검증 결합 (자동전진 없음)

### 5.1 `changeStage`에 게이팅 검증 추가

현행 `changeStage`(`journeys.service.ts:260`)는 게이팅이 없다. **전진(다음 단계)일 때** 현재 단계가 GATED면 전 품목 완료를 서버에서 재검증한다.

```ts
// changeStage 내부, target 결정(:282) 이후 · 트랜잭션(:306) 이전에 삽입
const currentMeta = stages.find((s) => s.code === journey.currentStageCode);
const isForward = target.sequenceNo > currentSeq;
if (isForward && currentMeta?.completionMode === 'GATED') {
  const gate = await this.gatingOf(journey, currentMeta);   // §4.2
  if (!gate.canComplete)
    throw new BusinessException(
      'STAGE_NOT_COMPLETE',
      '이 단계의 모든 품목이 완료되어야 다음 단계로 넘어갈 수 있습니다.',
      [{ field: 'toStageCode', reason: 'STAGE_ITEMS_INCOMPLETE' }],
      { targetCount: gate.targetCount, completedCount: gate.completedCount },
    );
}
```

- **후진**: 게이팅 검증 안 함. 현행처럼 `reason` 필수(`:295`)만 유지.
- **건너뛰기 전진**: 원칙적으로 현재 단계 게이팅만 검증(현장 유연성). 다단계 건너뛰기 시 중간 단계 게이팅은 강제하지 않는다(v1 "건너뛰기 허용" 철학 유지). §10 미결(엄격 검증 필요 여부).
- **자동 전진 절대 없음**: 게이팅이 열려도 `changeStage`는 담당자 호출로만 실행(D2).
- **낙관적 잠금**(`:273`)·이벤트 이력(`:307`)·감사로그(`:327`)·연락 제안(`:347`)은 현행 그대로.

## 6. [전체 완료] 시 비고 입력 + 진행상태 출력 (상태·완료일·비고)

### 6.1 비고 저장 — 기존 `JourneyEvent.notes` 재사용 (스키마 변경 없음)

`JourneyEvent.notes`가 이미 존재한다(`schema.prisma:1205`, `EVENT_SELECT`에 이미 포함 `journeys.service.ts:42`). `ChangeStageDto.notes`도 이미 있다(`journeys.dto.ts`). 즉 **[전체 완료] 시 비고는 추가 스키마 없이** `changeStage`의 `notes`로 흘려보낸다.

- 화면: [전체 완료] 클릭 → **비고 입력 화면**(필수 아님) → `POST /journeys/:id/stage { toStageCode, notes, version }`.
- 완료 시각(완료일)은 `JourneyEvent.changedAt`(`:1212`)이 그 단계를 떠난 시각 = 그 단계 완료 시각.

### 6.2 진행상태 출력에 3종 노출 (기존: 상태·완료일 → v2: 상태·완료일·비고)

`get()` 응답(`journeys.service.ts:243`)의 `stages[]`에 **각 단계의 완료 이력**을 접합해 내려준다.

```jsonc
// GET /journeys/:id — stages 항목 확장
"stages": [
  {
    "code": "BASTING_RECEIVED",
    "name": "가봉 입고",
    "sequenceNo": 5,
    "hasTemplate": true,
    "completionMode": "GATED",
    // 게이팅 현황 (§4)
    "targetCount": 3,
    "completedCount": 3,
    "canComplete": true,
    // v2 추가: 이 단계를 완료(=떠남)한 이벤트에서 파생
    "completed": true,
    "completedAt": "2026-07-20T02:11:00Z",   // JourneyEvent.changedAt
    "notes": "가봉 3벌 모두 확인, 고객 통화 완료"  // JourneyEvent.notes = 비고
  }
]
```

- 파생 규칙: 단계 `X`의 완료일/비고 = "`fromStageCode = X`인 가장 최근 전진 이벤트"의 `changedAt`/`notes`. 후진으로 다시 들른 경우 최신 것으로 갱신.
- 프런트 진행상태 카드/타임라인은 이 3종(상태·완료일·비고)을 단계별로 표기.

## 7. 맞춤+렌탈 동시진행 & 수선 대상 품목

### 7.1 맞춤+렌탈 (PDF 3번) — journey 2건 병행

현행 구조가 이미 이를 지원한다:
- `Order`는 `@@unique([contractId, transactionType])`(`schema.prisma:439`) — 한 계약이 CUSTOM 1건·RENTAL 1건 각각 가질 수 있음.
- journey 생성은 **주문 1건당 진행 1건**(중복 방지 `journeys.service.ts:172`).
- 따라서 한 고객이 CUSTOM·RENTAL 주문을 모두 가지면 → **CUSTOM journey + RENTAL journey 2건이 병행**된다. 추가 설계 불필요.
- 고객 상세 진행 카드는 `listByCustomer`(`:205`)가 2건을 모두 반환하므로 **2개 트랙을 나란히** 표시.

### 7.2 수선(REPAIR) 트랙의 대상 품목

- 수선은 order가 아닌 `RepairRequest`(`schema.prisma:921`) 기반. journey `orderId`는 비운다(nullable, `:1170`).
- REPAIR journey는 **수선 접수 등록 시 자동 생성**(§8), currentStage=`REPAIR_RECEIVED`(자동완료).
- 대상 품목 = 그 수선 건에 속한 `RepairRequest` 행들. `JourneyStageItemCompletion.targetType='REPAIR_ITEM'`, `targetId = RepairRequest.id`.
- 한 고객이 여러 수선 건을 동시에 가질 수 있으므로, "수선 1묶음 = journey 1건" 단위 정의가 필요 → §10 미결(수선 journey 단위: 접수 1건=journey 1건 vs 여러 수선요청 묶음). **기본안**: RepairRequest 1건 = journey 1건(단순), 대상 품목은 그 요청의 링크 대상(orderItem/component/rentalItem)들. 운영 피드백으로 묶음화 검토.

## 8. 고객 연락 연동 (기존 buildSuggestion 유지)

연락 단계(가봉입고/완성복입고/렌탈수선입고/수선입고 등, §4 ●표시)에서 **기존 연락 제안을 그대로** 쓴다.

- `changeStage`가 다음 단계 진입 시 `buildSuggestion`(`journeys.service.ts:352`)으로 치환 문구를 응답에 실어 보냄 → 화면 확인창(v1 05 §4 흐름 그대로). 발송은 별도 요청, 멱등키 `journey:{id}:{stageCode}`(`:359`).
- `get()`의 `currentSuggestion`(`:235`)도 유지 — 연락 단계 진입 후 재접속해도 [고객 연락] 버튼 상시 노출.
- 시드 템플릿(`journey-stage-seed.ts:13` `STAGE_TEMPLATES`) 보강:
  - 기존: `JOURNEY_BASTING_RECEIVED`, `JOURNEY_PRODUCT_RECEIVED`, `JOURNEY_RELEASED`, `JOURNEY_RENTAL_CHECKED_OUT`, `JOURNEY_RENTAL_RETURNED`.
  - v2 신규/재매핑: `JOURNEY_RENTAL_REPAIR_RECEIVED`(렌탈 수선 입고 안내), `JOURNEY_REPAIR_CHECKED_IN`(수선 입고 안내). 렌탈 트랙 개명에 맞춰 기존 `JOURNEY_RENTAL_CHECKED_OUT` 템플릿은 `RENTAL_REPAIR_CHECKED_OUT` 단계로 매핑 이동.
  - 수선 접수/완료 연락은 이미 `REPAIR_TEMPLATES`(`journey-stage-seed.ts:46`)로 존재하나, 이는 repairs 모듈의 `notification_rules(REPAIR:상태)` 경로다. REPAIR **journey 트랙**의 연락은 `journey_stages.templateId` 경로로 통일한다(중복 발송 방지) → **확정**(§8.1).

### 8.1 REPAIR 연락 경로 일원화 (구 §10.3 #5 — 확정)

수선 연락은 **journey `journey_stages.templateId` 경로 하나만** 쓴다. 구 `notification_rules(REPAIR:상태)` 경로는 폐지한다.

| 항목 | 결정 |
|---|---|
| 발송 경로 | journey `REPAIR_CHECKED_IN` 단계의 `JOURNEY_REPAIR_CHECKED_IN` 템플릿. 멱등키 `journey:{id}:REPAIR_CHECKED_IN` |
| `notification_rules(REPAIR:*)` | **미사용**. `repairs.service.createStatusEvent`는 `suggestedNotification: null` 고정. 유일한 소비 함수 `templateIdForTrigger`는 호출자 없음 |
| 데이터 | 규칙·템플릿 행은 물리삭제하지 않고 존치(과거 발송 이력의 templateId 참조 보존) |
| 관리자 화면 | `StageTemplateMappingCard`의 수선 탭도 다른 트랙과 동일하게 **journey 단계 4개**를 보여준다. 구 규칙 목록·사용 토글은 제거 — 설정해도 발송에 쓰이지 않는 항목을 노출하지 않기 위함 |

**수선 상태 자동 전이.** 연락 경로가 journey로 넘어가면서, 6단계 수선 상태(통합설계서 §12.1)의 `CUSTOMER_NOTIFIED`는 담당자가 손으로 한 번 더 눌러야 하는 껍데기 단계가 된다. 같은 사실을 두 번 입력하지 않도록, **수선 입고 안내를 실제로 발송하면**(`notification-outcome` = `SENT`) 수선 건 상태를 `RETURNED_TO_SHOP` → `CUSTOMER_NOTIFIED`로 함께 옮긴다(`journeys.service.syncRepairNotified`).

- 6단계 원문은 그대로 둔다 — 상태를 줄이면 v1 §12.1 변경과 기존 데이터 마이그레이션이 따라온다.
- 직전 상태가 `RETURNED_TO_SHOP`일 때만 옮긴다. 수선 상태는 한 칸씩만 전진하므로(`repairs.service.validateStatusTransition`) 그 밖의 상태에서 밀어넣으면 순서가 깨진다.
- 어긋나면 조용히 건너뛴다. 연락은 이미 나갔고 되돌릴 수 없으므로 발송 결과 기록을 실패시켜서는 안 된다.
- `RepairStatusEvent`와 감사로그를 남겨 누가·언제 옮겼는지 추적한다.

- 완성복 입고 시 production 쪽 자동 제안(`production.service.ts:260` `buildReceivedSuggestion`)과 journey PRODUCT_RECEIVED 연락이 **이중 발송될 수 있다**. 멱등키가 다르므로(`production:{itemId}:RECEIVED` vs `journey:{id}:PRODUCT_RECEIVED`) 두 번 나갈 위험 → §10 미결(제안 출처 일원화; journey 우선 권장).

### 9.2 자동완료(AUTO) 단계 훅

수동 버튼이 없는 AUTO 단계는 도메인 이벤트에서 journey를 전진/생성시킨다.

| 단계 | 트리거 | 구현 지점 |
|---|---|---|
| CUSTOM/RENTAL `CONTRACT_CONFIRMED` | 계약 "계약완료" 액션 | `contracts.service.ts` confirm 트랜잭션에서 해당 order의 journey를 CONTRACT_CONFIRMED로 전진(없으면 생성) |

### 10.3 미결사항

1. **CONSULT_DONE(초도 상담) 제거 여부** — PDF엔 journey 단계로 없으나, 상담 완료를 별도 단계로 볼 실무 필요가 있으면 유지. 기본안: 제거(상담 예약 1단계로 통합).
2. **CONSULT_RESERVED 자동종료** — 스케줄러 없이 지연평가(get/list) 기본안. 배치가 꼭 필요하면 경량 cron 재도입 검토.
3. **수선 journey 단위** — RepairRequest 1건=journey 1건(기본안) vs 여러 수선요청 묶음(§7.2).
4. **연락 제안 이중발송** — production `buildReceivedSuggestion`(`production.service.ts:260`)와 journey PRODUCT_RECEIVED 연락 출처 일원화(§8). journey 우선 권장.
5. ~~**REPAIR 연락 경로 통합**~~ — **확정**: journey `journey_stages.templateId` 단일 경로. 발송 시 수선 상태 `CUSTOMER_NOTIFIED` 자동 전이까지 포함(§8.1).
6. **다단계 건너뛰기 시 중간 단계 게이팅** — 현재 단계만 검증(기본안) vs 전 구간 강제.
7. **완료 취소 권한/시점** — 다음 단계 전진 후 이전 단계 품목 완료 취소 허용 여부.
