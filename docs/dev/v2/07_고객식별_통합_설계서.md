## §0. 결정 요약

**목적** — 고객을 "가망 고객 / 계약 고객"으로 **구분해 저장**하던 방식을 폐기한다. 접점이 생긴 사람은 **모두 고객으로 등록**하고, 화면마다 **필요한 고객만 골라 보여준다**.

| # | 항목 | 현행(as-is) | 변경(to-be) | 결정 |
|---|---|---|---|---|
| D1 | 고객 식별 축 | `registeredAt`(미등록/등록) **+** `customerStatus`(PROSPECT/CONTRACTED) 2축 | **1축 폐기.** 모든 고객은 생성 즉시 등록 고객 | 확정 |
| D2 | 예약 고객 | 예약 시 `registeredAt=null`인 미등록 행 생성 → 별도 모달에서 등록 | 예약 등록 = **고객 등록**. `registeredAt` 즉시 기록 | 확정 |
| D3 | 고객 메뉴 노출 기준 | `registeredAt != null AND customerStatus='CONTRACTED'` | **계약 보유 고객**(DRAFT·CONFIRMED·CANCELLED 무관). 상단 [계약 고객 / 전체 고객] 토글로 전체 조회 가능 | 확정 |
| D4 | 예약 메뉴 목록 뷰 | 기간 RangePicker + 목적·상태·출처 3셀렉트, 이름 검색 없음 | **통합 검색 1필드** + 기간. 기본 `오늘 이후` × `RESERVED·CONFIRMED` | 확정 |
| D5 | 예약 캘린더(일/주/월)·인쇄 | 선택 날짜 기준 전체 표시 | **현행 유지.** D4 필터는 목록 뷰에만 적용 | 확정 |
| D6 | 계약서 신규 흐름 | 고객 검색 팝업 → 곧바로 계약서 | 고객 검색 팝업 → **필수 정보 결손 시 보완 입력** → 계약서(계약 구분 선택) | 확정 |
| D7 | 계약 전 필수 고객 정보 | 정의 없음 | `heightCm` · `weightKg` · `age` (엑셀 작업지시서 연동, plan_v2 §고객) | 확정 |

**스키마 변경 없음.** `registeredAt` 컬럼은 유지하되 의미를 바꾸고 데이터만 백필한다(§5).

## §1. 데이터 모델 — `registeredAt` 의미 변경

### 1.1 왜 컬럼을 지우지 않는가
`registeredAt`은 감사로그 `before/after` 스냅샷(`audit_logs`)에 이미 다수 기록되어 있다. 컬럼을 drop하면 과거 스냅샷과 현재 스키마가 어긋나 감사 추적이 깨진다. **컬럼은 남기고 의미를 재정의**한다.

| | 현행 | 변경 |
|---|---|---|
| 의미 | 예약 자동생성 고객을 정식 고객으로 승격한 시각. null = 미등록 | **고객 행이 생성된 시각.** null 불허(백필) |
| 쓰는 곳 | 고객 목록 where, 예약 `customerRegistered` 필터, 고객모드 승격 분기 | **필터 용도 전면 제거.** 표시·감사용으로만 |

`schema.prisma:181` 의 주석을 아래로 교체한다.

```prisma
/// 고객으로 등록된 시각. 예약 자동생성분을 포함해 모든 고객 행에 채워진다(v2 설계서 07 D2).
registeredAt    DateTime? @map("registered_at") @db.Timestamptz(6)
```

### 1.2 `customerStatus` 역할 축소 (D8)

| 값 | 현행 용도 | 변경 후 |
|---|---|---|
| `PROSPECT` | 고객 목록에서 숨김 + "미계약" 배지 | **필터에서 제외.** 배지 표시도 제거 |
| `CONTRACTED` | 고객 목록 기본 필터 | 배지 표시 제거. 계약 확정 시 기록은 **유지**(`contractedAt`과 함께 이력값) |
| `INACTIVE` | 비활성 | **유지.** 모든 목록에서 제외하는 유일한 상태값 |

> `PROSPECT`/`CONTRACTED` 값 자체는 계속 기록한다(계약 확정 트랜잭션 `contracts.service.ts:417-426` 그대로). **조회 조건과 화면 배지에서만 걷어낸다.** 값을 없애면 되돌릴 수 없고, 남겨두면 언제든 다시 쓸 수 있다.

## §2. 고객 메뉴 (CUST-001)

### 2.1 노출 기준 (D3)

```
scope = CONTRACT (기본)  →  customerStatus != 'INACTIVE'  AND  contracts: { some: {} }
scope = ALL              →  customerStatus != 'INACTIVE'
```

- `contracts: { some: {} }` — 계약 상태를 가리지 않는다. **작성중(DRAFT)·취소(CANCELLED)도 포함**한다. "계약서를 한 번이라도 연 고객"이 곧 고객 메뉴의 대상이다.
- 기존 `registeredAt: { not: null }` 조건은 삭제한다.

### 2.2 API 변경 — `CustomerListQueryDto`

| 파라미터 | 현행 | 변경 |
|---|---|---|
| `status` | 기본값 `'CONTRACTED'` | **기본값 제거**(옵셔널). 명시 지정 시에만 필터 |
| `includeProspect` | PROSPECT 추가 포함 | **deprecated.** 파싱은 유지하되 무시(호출부 정리까지 무해 통과) |
| `scope` | — | **신설.** `'CONTRACT' \| 'ALL'`, 기본 `'CONTRACT'` |

`customers.service.ts:60-67` 를 다음으로 교체한다.

```ts
// 비활성 고객은 어떤 목록에도 나오지 않는다(설계서 07 D8).
const where: Prisma.CustomerWhereInput = { customerStatus: { not: 'INACTIVE' } };
// 고객 메뉴 기본은 "계약이 한 건이라도 있는 고객" — 작성중·취소 계약도 포함한다(D3).
if ((query.scope ?? 'CONTRACT') === 'CONTRACT') where.contracts = { some: {} };
if (query.status) where.customerStatus = query.status;   // 명시 지정 시에만
```

> `where.customerStatus`가 두 번 배정되므로 `status` 명시 시 INACTIVE 제외가 덮인다. 실제 구현에서는 `AND` 배열로 합성해 두 조건이 모두 살아있게 한다.

### 2.3 화면 변경 — `CustomersPage.tsx`

| 위치 | 현행 | 변경 |
|---|---|---|
| 상단 버튼 | [예약 고객 등록] · [고객 등록] | **[예약 고객 등록] 제거**(개념 소멸). [고객 등록]은 유지 |
| 검색 조건 | 통합 검색 + 진행상태 Segmented(전체/진행중/완료) | **범위 Segmented 추가**: [계약 고객 / 전체 고객], 기본 `계약 고객`. 진행상태 Segmented는 유지 |
| 고객 상태 열 | 계약상태 배지 + 진행단계 배지 | **진행단계 배지만**(2026-07-27 적용 완료, `CustomersPage.tsx:83-94`) |

- [고객 등록]으로 만든 고객은 계약이 없어 기본 범위에서 보이지 않는다. **등록 성공 시 범위를 `전체 고객`으로 자동 전환**해 방금 만든 행이 보이게 한다(등록 직후 사라지는 UX 방지).

### 2.4 알려진 비대칭 — 계약 건수·잔금 집계

목록 노출은 취소 계약을 **포함**하는데, `계약 건수`·`잔금` 집계는 `status != 'CANCELLED'`만 센다(`customers.service.ts:135`). 따라서 **취소 계약만 있는 고객은 목록에 "1건 아님 / 0건 · 0원"으로 표시된다.**

- **집계 기준은 바꾸지 않는다.** 잔금은 회계적 의미가 있어 취소 계약을 더하면 안 된다.
- 대신 `계약 건수` 열의 툴팁/보조 표기로 "취소 제외"임을 밝힌다. 0건인데 목록에 있는 행은 취소 계약만 보유한 고객이다.

## §3. 예약 메뉴 (APPT-001)

### 3.1 목록 뷰 필터 (D4)

| 조건 | 기본값 | 비고 |
|---|---|---|
| 기간 | `오늘 ~ 제한 없음` (`from = today`, `to` 없음) | 사용자가 RangePicker로 변경 가능 |
| 상태 | `RESERVED`, `CONFIRMED` | 방문완료·취소·노쇼 제외 = "앞으로 맞이할 손님" |
| 검색 | 통합 검색 1필드 | 고객명 · 전화번호 · 예약 목적명 부분일치 |

현행 기본값 `[오늘-7일, 오늘+7일]`(`AppointmentsPage.tsx:187`)을 `[오늘, null]`로 바꾼다.

### 3.2 통합 검색 필드

- **제거**: 예약 목적 Select(multi), 상태 Select(multi), 출처 Select — `AppointmentsPage.tsx:343-373`
- **추가**: 검색 Input 1개 → 백엔드 `q` 파라미터로 전달. `fetchAppointments`는 이미 `q`를 지원하므로 프런트 연결만 하면 된다(`api/appointments.ts:138`).
- 백엔드 `q` 검색 범위를 확장한다 — `appointments.service.ts:98-106`:

```ts
// 고객명·전화번호에 더해 예약 목적명까지 한 필드로 검색한다(설계서 07 D4).
const or: Prisma.AppointmentWhereInput[] = [
  { customer: { name: { contains: keyword, mode: 'insensitive' } } },
  { purpose: { name: { contains: keyword, mode: 'insensitive' } } },
];
if (digits) or.push({ customer: { phoneNormalized: { contains: digits } } });
where.OR = or;
```

> **주의**: 현행은 `customerWhere`(고객 하위 조건)에 OR을 걸지만, 목적명은 `purpose` 관계라 같은 OR에 들어갈 수 없다. **`where.OR` 최상위로 끌어올려야** 한다. `customerId`·`status` 등 다른 조건과 AND로 결합되는지 반드시 확인한다.

### 3.3 캘린더·인쇄는 손대지 않는다 (D5)

일/주/월 뷰(`Timetable`, `MonthCalendar`)와 인쇄(`openPrint`, `AppointmentsPage.tsx:236`)는 선택 날짜 기준으로 **과거 예약과 취소 예약을 모두 그대로** 보여준다. 과거 방문 이력 확인·일정표 인쇄가 캘린더의 본래 목적이기 때문이다. §3.1의 기본값은 `mode === 'list'`일 때만 적용한다.

## §4. 계약서 신규 흐름 (CONT-002)

### 4.1 흐름

```
[신규 계약] 버튼
  → 고객 검색 팝업 (전 고객 대상 — 계약 유무 무관)
  → 고객 선택
  → 필수 정보 결손 검사 (키·체중·나이, D7)
       결손 있음 → [고객 정보 보완] 모달 → PATCH /customers/:id
       결손 없음 → 통과
  → 계약서 작성 화면
  → 계약 구분 선택 (기본 품목 라인 자동 복사)
```

### 4.2 각 단계 변경점

| 단계 | 현행 | 변경 |
|---|---|---|
| 고객 검색 팝업 | "미계약 고객 포함" Switch(기본 on) — `CustomerPickerModal.tsx:104` | **Switch 제거.** 전 고객이 검색 대상(§2.2 `scope=ALL`로 호출). "상태" 열도 제거 |
| 고객 선택 후 | 곧바로 `customerId`를 URL에 실음 | **결손 검사 후** 보완 모달 → 통과 시 URL 반영 |
| 계약 구분 | 계약서 화면 필수 Select — `ContractFormPage.tsx:511-521` | **변경 없음. 이미 요구사항을 충족한다** |

### 4.3 필수 정보 결손 판정 (D7)

```ts
/** 계약서 작성 전 채워져 있어야 하는 고객 정보 (설계서 07 D7 — 엑셀 작업지시서 연동) */
const CONTRACT_REQUIRED_FIELDS = ['heightCm', 'weightKg', 'age'] as const;
const isIncomplete = (c: CustomerSummary) =>
  CONTRACT_REQUIRED_FIELDS.some((f) => c[f] == null);
```

- **프런트 게이트만 둔다.** 백엔드 계약 확정(`POST /contracts/:id/confirm`)에는 이 검증을 넣지 않는다. 이미 저장된 계약이 소급 실패하면 안 되고, 신체 정보는 채촌 단계에서 정정될 수 있기 때문이다.
- 보완 모달은 [건너뛰기]를 제공하지 않는다. 다만 "나중에 채촌에서 정정할 수 있습니다" 안내 문구를 둔다.
- 기존 계약을 이어서 작성(`?contractId=`)하는 경로에는 게이트를 걸지 않는다. 신규 진입만 대상이다.

## §5. 마이그레이션

단일 마이그레이션 `20260727_v2_customer_identity_unify` — **DDL 없음, 데이터 백필만.**

```sql
-- 예약으로 자동 생성된 미등록 고객을 모두 등록 고객으로 승격한다(설계서 07 D2).
-- 등록 시각은 최초 예약일이 있으면 그것을, 없으면 행 생성 시각을 쓴다.
UPDATE customers
   SET registered_at = COALESCE(registered_at, first_reserved_at, created_at)
 WHERE registered_at IS NULL;
```

- **롤백**: 되돌릴 필요가 없다. `registered_at`이 채워져도 어떤 기능도 깨지지 않으며(필터가 사라지므로), 원복하려면 코드만 되돌리면 된다.
- `customerStatus`는 건드리지 않는다. PROSPECT로 남은 값이 그대로 있어도 새 조회 조건과 무관하다.

## §7. 파급·미결

### 7.1 계약 확정 시 진행(journey) 자동 생성 — **본 설계서에 포함**
기존에는 `CustomerJourney`가 **수동 생성(`POST /journeys`)** 또는 **수선 접수 시 자동 생성**만 존재했다. 계약 확정은 기존 journey를 전진시킬 뿐 새로 만들지 않아(`journeys.length === 0`이면 즉시 return), 계약 고객이 늘어나면 진행상태 열이 `-`인 행이 다수 발생한다.

plan_v2 §진행상태의 "상담 - 계약 - 스타일 컨설팅 …" 흐름대로 **계약 확정을 진행의 시작점**으로 삼는다.

**`ensureJourneysForOrders(tx, customerId, orders, confirmedAt, actorId)`** — 계약 확정 트랜잭션에서 `syncOrdersToVersion` 직후, 기존 전진 훅보다 먼저 실행한다.

| 상황 | 처리 |
|---|---|
| 주문에 연결된 진행이 이미 있음(취소 제외) | 건너뜀 — 주문 1건당 진행 1건 규칙 유지 |
| 상담 단계에서 수동 생성한 미연결 진행(`orderId=null`)이 같은 트랙에 ACTIVE로 있음 | **그 진행을 흡수**해 주문을 연결하고 `CONTRACT_CONFIRMED`로 전진. 새로 만들지 않는다 |
| 둘 다 없음 | `CONTRACT_CONFIRMED` 단계에서 신규 생성 |
| 트랙에 단계 정의가 없음(시드 미적용) | 건너뜀 — 계약 확정 자체를 막지 않는다 |

어느 경로든 `JourneyEvent`를 남기고 감사로그를 기록한다. 주문은 계약당 CUSTOM·RENTAL 각 최대 1건이므로, 맞춤+렌탈 동시 계약이면 진행도 2건 생성된다(plan_v2 §진행상태 3항).

### 7.1.1 진행상태 `완료` 필터 정의 수정
`progress=DONE`에 `customerStatus='CONTRACTED'` OR 절이 있어 **계약 확정 고객 전원이 "완료"로 분류**되고 있었다. 계약 확정은 진행의 시작이지 완료가 아니다 — 해당 절을 제거했다.

```
DONE = journeys.some(status='COMPLETED')  AND  journeys.none(status='ACTIVE')
```

### 7.2 전화번호 없는 예약
`customers.phone_normalized`는 unique·not null이다. 전화번호 없는 예약은 고객 행을 만들 수 없다. 현행도 동일 제약(`CreateAppointmentDto` — `customerId` 없으면 `phone` 필수, 네이버 어댑터도 `phone: string` 필수)이므로 **정책 변경 없음**.

### 7.3 고객모드 영향 (후속)
`CustomerSearchPage.tsx:92-107`의 "예약 고객 → 정식 등록 승격" 분기는 `registeredAt`이 항상 채워지므로 **항상 '이미 등록된 고객' 경로**로 흐른다. 동작은 정상(해당 고객으로 이동)이나 죽은 코드가 된다. 관리자 모드 적용 완료 후 별도로 정리한다.

## §8. 테스트 항목

**고객**
- 계약이 없는 고객이 기본 범위에서 안 보이고, [전체 고객] 토글에서 보인다
- DRAFT 계약만 있는 고객이 기본 범위에 나온다 (현빈 케이스 — 회귀 기준점)
- CANCELLED 계약만 있는 고객이 목록에 나오고 계약 건수는 0건이다
- INACTIVE 고객은 두 범위 모두에서 안 보인다
- [고객 등록] 성공 시 범위가 전체로 전환되어 방금 만든 행이 보인다

**예약**
- 목록 뷰 기본값이 오늘 이후 · RESERVED/CONFIRMED다
- 통합 검색이 고객명·전화·목적명 모두에 걸린다
- 통합 검색과 기간·`customerId` 조건이 AND로 결합된다 (§3.2 주의사항)
- 일/주/월 캘린더는 과거·취소 예약을 그대로 보여준다
- 인쇄가 현행대로 동작한다

**계약**
- 신규 계약 → 고객 선택 → 키·체중·나이 결손 시 보완 모달이 뜬다
- 보완 저장 후 계약서로 진행되고, `customerId`가 URL에 실린다
- 이미 채워진 고객은 모달 없이 통과한다
- `?contractId=`로 이어서 작성할 때는 게이트가 걸리지 않는다
- 계약 구분 선택 시 기본 품목 라인이 복사된다 (회귀)
