## 1. 배경 — 현행 채촌 vs v2

v1(09 문서)에서 채촌은 **주문 비종속 독립 화면**으로 승격됐다(검색·CRUD·비교·잠금). 그러나 저장·출력은 여전히 **숫자 치수(cm)만** 다룬다. plan_v2는 여기에 세 축을 더한다.

| 축 | 현행 (근거) | v2 요건 (결정) |
|---|---|---|
| 이미지 | 채촌 도메인 이미지/파일 기능 **전무** (grep 0건). 범용 `EntityFile`만 존재 | 세션당 사진 ≤50장 첨부, 선택분 A4 인쇄 (**A4**) |
| 단위 | `unit` 컬럼 저장만(기본 `CM`, `measurements.service.ts:775`). 변환 로직 **전무**(grep `2.54` 0건). 비교 diff는 동일단위 가정 | 저장은 CM 유지, 화면 전체 cm↔inch 전환 버튼, 엑셀 신체열 cm·완성(인치)열 inch (**A3**) |
| 앞마다/뒷마다 | 카탈로그에 없음. `FRONT_RISE(앞밑윗길이)`/`BACK_RISE(뒤밑윗길이)`는 이미 존재하고 엑셀 신체열(F, 67·69행)에 매핑됨(`work-order-template-map.ts:102-103`) | 앞마다/뒷마다를 **신규 하의 항목**으로 추가, 엑셀 **하의 추가요청사항(앞/뒤)** 매핑 (**D8**) |

설계 불변식: **EAV 스키마·독립 화면·잠금 규칙(`assertNotLocked`, `measurements.service.ts:786`)은 유지**한다. v2는 카탈로그 상수 2건 + 이미지 연동(EntityFile) + 프런트 표시/인쇄 로직을 얹는 **가산 변경**이며, `MeasurementSession`/`MeasurementValue` 컬럼은 건드리지 않는다.

## 2. 앞마다/뒷마다 신규 항목 (D8)

### 2.1 카탈로그 신규 코드

`backend/src/modules/measurements/measurement-catalog.ts:29-37`(하의 LOWER 블록) 끝에 2건 추가한다. `FRONT_RISE`(앞밑윗길이)·`BACK_RISE`(뒤밑윗길이)는 **밑위 길이**이고, 앞마다/뒷마다(股, mata)는 **밑아래 재단선**으로 별개 항목이다 — 혼동을 막기 위해 코드는 `RISE`와 명확히 다른 접미사를 쓴다.

```ts
// 하의 (measurement-catalog.ts, PANTS_LENGTH sortOrder 280 뒤)
  { code: 'FRONT_MADA', label: '앞마다', bodySection: 'LOWER', valueType: 'NUMERIC', sortOrder: 290 },
  { code: 'BACK_MADA',  label: '뒷마다', bodySection: 'LOWER', valueType: 'NUMERIC', sortOrder: 300 },
```

> 코드명 제안: `FRONT_MADA / BACK_MADA`. 대안 `FRONT_CROTCH / BACK_CROTCH`. **`FRONT_RISE/BACK_RISE`와 절대 병합하지 않는다**(00 §2 D8: "매핑되어 있으면 신규 추가"). 셔츠(300)·구두(410) sortOrder와 겹치지 않게 290/300을 쓰되, 셔츠 SHIRT_NECK(300)과 숫자만 같고 bodySection이 달라 정렬 충돌 없음(정렬은 bodySection 그룹 내에서만 의미).

미등록 코드도 EAV로 저장 가능하지만(카탈로그 없으면 `bodySection='ETC'`, `sortOrder=900`, `measurements.service.ts:772,776`), **카탈로그 등록이 있어야** 화면 라벨·정렬·엑셀 매핑이 자동 보완되므로 반드시 상수에 추가한다.

### 2.2 엑셀 매핑 — 하의 추가요청사항(앞/뒤)

현행 `applyMeasurements`(`work-order-excel.ts:258`)는 `MEASUREMENT_ROW_MAP`에 있는 코드만 신체열(F)에 쓰고, 없는 코드는 `unmapped[]`에 담아 **상의 비고(`CELL.upperNote='AA41'`)의 `[치수]` 줄**로 흘려보낸다(`:263, :332`). 앞마다/뒷마다는 **하의 요청사항 칸(`CELL.lowerNote='AA75'`)에 앞/뒤 라벨로** 명시 출력해야 하므로 전용 처리를 추가한다.

설계:

1. `work-order-template-map.ts`에 하의 요청사항 매핑 상수를 신설한다(신체열 행 매핑이 아니라 **비고칸 라벨 매핑**임을 명확히 분리).

   ```ts
   // work-order-template-map.ts
   /** 신체열에 넣지 않고 '하의 추가요청사항'(AA75)에 라벨과 함께 쓰는 채촌 코드 */
   export const LOWER_NOTE_MEASUREMENTS: ReadonlyArray<readonly [string, string]> = [
     ['FRONT_MADA', '앞'],
     ['BACK_MADA', '뒤'],
   ];
   export const LOWER_NOTE_MEASUREMENT_MAP: ReadonlyMap<string, string> = new Map(LOWER_NOTE_MEASUREMENTS);
   ```

2. `applyMeasurements`(`work-order-excel.ts:258-274`)를 확장한다. 반환을 `{ unmapped, lowerNotes }` 형태로 바꿔, 하의 요청사항 라인을 별도로 넘긴다.

   ```ts
   function applyMeasurements(ws, measurements) {
     const unmapped: string[] = [];
     const lowerNotes: string[] = [];               // ← 추가
     for (const m of measurements) {
       const lowerLabel = LOWER_NOTE_MEASUREMENT_MAP.get(m.code);   // 앞/뒤
       if (lowerLabel) { lowerNotes.push(`${lowerLabel} ${m.value}`); continue; }
       const row = MEASUREMENT_ROW_MAP.get(m.code);
       if (!row) { unmapped.push(`${m.label} ${m.value}${m.unit === 'CM' ? 'cm' : ''}`); continue; }
       // …기존 신체열 기입…
     }
     return { unmapped, lowerNotes };               // ← 변경
   }
   ```

3. `buildWorkOrderWorkbook`(`work-order-excel.ts:326`)에서 `lowerNotes`를 하의 요청사항 칸(`CELL.lowerNote='AA75'`)에 기입한다. 상의 비고(AA41)의 `[치수]` 처리와 대칭.

   ```ts
   const { unmapped: unmappedMeasurements, lowerNotes } = applyMeasurements(ws, data.measurements);
   // …상의 비고(upperNote) 처리 뒤…
   if (lowerNotes.length > 0) {
     const lowerCell = ws.getCell(CELL.lowerNote);           // AA75
     const printed = printedText(lowerCell.value);           // 인쇄 보조문구 보존
     lowerCell.value = [printed, `[마다] ${lowerNotes.join(' / ')}`].filter(Boolean).join('\n');
     lowerCell.alignment = { ...(lowerCell.alignment ?? {}), wrapText: true, vertical: 'top' };
   }
   ```

`work-orders.service.ts:610-615`의 `measurements` 스냅샷 매핑은 **변경 불필요** — 이미 모든 값을 `{code,label,value,unit}`로 전달하므로, 신규 코드가 카탈로그에 있으면 자동 포함된다.

`NOT_FILLABLE_FIELDS`(`work-order-template-map.ts:135`)에서 관련 항목("바지기장 앞/뒤" 등)은 앞마다/뒷마다와 별개이므로 그대로 둔다.

## 3. cm/inch 전환 (A3)

### 3.1 원칙

- **저장은 CM 고정.** `MeasurementValue.numericValue`(Decimal(8,2))·`unit='CM'`를 그대로 유지한다. DB·API 계약·비교(diff) 모두 CM 기준이라 스키마/서버 변경 없음.
- inch는 **표시 전용 파생값**이다. `inch = round(cm / 2.54, 1)` — **소수 1자리 반올림**(예: 96cm → 37.8in). cm는 카탈로그가 NUMERIC이면 소수 1자리 관례 유지.
- 전환은 **화면 전체 토글**(치수 그리드 전체가 동시에 cm↔inch로 표시)이며, 단위 상태는 세션에 저장하지 않는다(항상 CM 로드 → 화면에서 계산 표시).

### 3.2 화면 처리 (프런트)

- `MeasurementEditPage.tsx`·`MeasurementComparePage.tsx` 상단 기능 버튼 줄에 **`[cm] / [inch]` 세그먼트 토글**을 둔다. 상태 배지는 텍스트+단위 병기(02 표준 §2 색상단독 금지 준수).
- 표시: 저장된 cm 값에 대해 토글이 inch면 `cm/2.54` 반올림값을 렌더. 원본 cm는 항상 보관.
- **편집 시 단위 처리(핵심)**: inch 모드에서 입력한 값은 **저장 직전 CM으로 역환산**한다(`cm = inch * 2.54`, Decimal(8,2) 반올림). 즉 화면 단위와 무관하게 서버로는 항상 CM을 전송한다. `NumericKeypad`(v1 §2, 물리 키패드 입력 최근 지원)는 현재 단위 라벨만 바꿔 재사용한다.
- 반올림 왕복 오차 방지: inch로 보고 있다가 편집하지 않은 항목은 **원본 cm를 그대로 전송**(재환산 금지). 사용자가 실제로 편집한(값이 바뀐) 항목만 inch→cm 역환산해 전송한다.
- 비교(compare) 화면: 서버 diff는 CM 그대로 계산되므로, inch 표시일 때는 각 side와 diff를 `/2.54`로 렌더만 한다(백엔드 compare 응답 불변).

### 3.3 엑셀 — 신체열(cm) + 완성(인치)열(inch)

조사 결과: **완성(인치)/완성(센치) 열은 양식에 이미 존재**한다(`work-order-template-map.ts:155` — "채촌: 수정·완성(인치)·완성(센치) 열 … 데이터 없어 공란"). 즉 열은 있으나 좌표가 아직 매핑되지 않았다.

설계:

1. 완성(인치) 열의 실제 좌표 열문자를 확정한다. 현행 신체열은 `BODY_COLUMN='F'`(`work-order-template-map.ts:82`), 행은 `MEASUREMENT_ROW_MAP`(상의 21~41, 하의 61~75)로 공유된다. 완성(인치)/완성(센치)는 **같은 행, 다른 열**이다.

   ```ts
   // work-order-template-map.ts (열문자는 템플릿 실측으로 확정 — §7 미결)
   export const BODY_COLUMN = 'F';           // 신체(cm) — 현행
   export const FINISH_INCH_COLUMN = '?';    // 완성(인치) — 템플릿에서 좌표 확인 후 확정
   // 완성(센치) 열은 신체(cm)와 동일값 중복이므로 A3 결정상 채우지 않는다(신체열=cm로 충분).
   ```

2. `applyMeasurements`에서 신체열 기입과 동시에 완성(인치) 열에 `round(cm/2.54,1)`를 쓴다.

   ```ts
   const cmCell = ws.getCell(`${BODY_COLUMN}${row}`);   // 기존 신체열
   // …기존 신체열 기입…
   const inch = Math.round((Number(m.value) / 2.54) * 10) / 10;
   if (Number.isFinite(inch)) {
     const inchCell = ws.getCell(`${FINISH_INCH_COLUMN}${row}`);
     inchCell.value = inch;
     fitFontSize(ws, `${FINISH_INCH_COLUMN}${row}`, String(inch));
   }
   ```

   문자값(SHOE_SIZE 등 valueType TEXT)은 inch 변환 대상이 아니므로 숫자 파싱 실패 시 건너뛴다.

3. 앞마다/뒷마다는 신체열 매핑이 아니라 하의 요청사항(§2.2)으로 나가므로 완성(인치) 열 대상이 아니다. 요청사항 라벨 값은 cm 그대로 적는다(요구 원문: 하의 요청사항 앞/뒤 매핑).

> 완성(센치) 열은 신체(cm) 열과 값이 동일해 A3 상 별도 채움 불필요. §7 미결로 남겨 현업 확인.

## 4. 이미지 업로드 (A4)

### 4.1 저장 모델 — 범용 EntityFile 재사용 (스키마 변경 없음)

옵션(`OptionChoice.imageFileId`)과 달리 채촌은 **다대일 첨부**이므로 범용 `EntityFile`(`schema.prisma:136-148`)을 쓴다. `MeasurementSession`에 컬럼을 추가하지 않는다.

| EntityFile 필드 | 채촌 값 |
|---|---|
| `entityType` | `'MEASUREMENT_SESSION'` (VarChar(50)) |
| `entityId` | `measurementSession.id` |
| `purpose` | `'PHOTO'` (VarChar(30)) |
| `fileId` | `File.id` (files 업로드 결과) |

`@@index([entityType, entityId])`(`schema.prisma:146`)로 세션별 조회 최적. `File` 삭제는 참조 있으면 거부(`files.service.ts:123-130`)라 무결성 보장. 허용 확장자에 이미지 포함(`png/jpg/jpeg/webp`, `files.service.ts:13`) — 그대로 사용.

**마이그레이션 없음.** 값은 데이터, 스키마 불변(00 §4: "채촌 이미지 — EntityFile 연동, 스키마 변경 최소").

### 4.2 업로드 흐름 (2단계 재사용)

기존 `POST /files`(`files.controller.ts:21`, `FILE_UPLOAD`)로 파일을 올려 `fileId`를 받고, 채촌 세션에 **연결(EntityFile 생성)**하는 얇은 엔드포인트를 추가한다.

| 메서드 | 경로 | 권한 | 설명 |
|---|---|---|---|
| GET | `/measurements/:id/images` | `MEASUREMENT_VIEW` | 세션 첨부 이미지 목록(정렬: createdAt) |
| POST | `/measurements/:id/images` | `MEASUREMENT_EDIT` | `{ fileId }` 를 세션에 연결(EntityFile 생성). **50장 초과 거부** |
| DELETE | `/measurements/:id/images/:entityFileId` | `MEASUREMENT_EDIT` | 연결 해제(EntityFile 삭제) + 참조 없으면 File 정리 |

동작 규칙:

- **개수 제한(50)**: 연결 전 `prisma.entityFile.count({ where: { entityType:'MEASUREMENT_SESSION', entityId, purpose:'PHOTO' } })`가 50 이상이면 `VALIDATION_ERROR`(field=`images`, reason=`MAX_50_EXCEEDED`). plan_v2: "최대 50장 초과 안 함".
- **잠금 규칙 적용 여부**: 이미지 첨부/삭제는 치수 편집이 아니므로 **`assertNotLocked` 대상에서 제외**(작업지시서 출력 후에도 사진 추가 허용). 단 세션 존재·소유 검증은 한다. → §7 미결(현업 확인). 보수적 기본값은 "제외".
- 응답 뷰는 `files.service.ts:toView`의 `downloadUrl`(`/api/v1/files/:id`)을 그대로 노출해 프런트가 `<img src>`로 렌더.
- 감사로그: `AuditService.log`로 `action=LINK/UNLINK`, `entityType='MEASUREMENT_SESSION_IMAGE'` 명시 호출(02 §1.6).

> `POST /measurements/:id/images`는 `{ fileId }` 본문형(2단계)을 기본으로 한다. 선택: multipart 단일 엔드포인트(업로드+연결)를 편의 래퍼로 추가 가능하나, files 모듈 재사용·감사 일관성 위해 2단계를 권장.

### 4.3 화면 배치

- **업로드 버튼 위치 = 기능 버튼 위치**(plan_v2): `MeasurementEditPage` 상단 기능 버튼 줄(임시저장/완료/삭제/단위토글 옆)에 `[사진 업로드]`.
- **출력 위치 = 제일 하단 갤러리**(plan_v2): 치수 그리드 아래 최하단에 썸네일 갤러리(그리드). 각 썸네일에 삭제(✕)·선택 체크박스.
- 드래그 다중 선택 또는 개별 체크박스로 인쇄 대상 지정(§5).
- AntD `Upload` 컴포넌트 사용, `beforeUpload`로 이미지 확장자·현재 개수(50) 프런트 선검증.

## 5. 이미지 A4 출력 (프런트 print)

plan_v2: "출력 이미지 개수 지정(체크박스 or 전체 드래그), 선택된 개수만큼 A4 한 장에 출력." 백엔드 개입 없이 **프런트 `@media print`**로 처리한다.

- 갤러리에서 선택한 N장을 전용 인쇄 레이아웃(`MeasurementPhotoPrint` 컴포넌트 또는 라우트 `/measurements/:id/print`)으로 넘겨 `window.print()`.
- **A4 한 장 고정** + 선택 개수별 그리드(가로 우선, 사진 aspect 유지, `object-fit: contain`):

  | 선택 장수 N | 그리드 | 비고 |
  |---|---|---|
  | 1 | 1×1 | 전면 |
  | 2 | 1×2 (세로 2분할) | |
  | 3~4 | 2×2 | |
  | 5~6 | 2×3 | |
  | 7~9 | 3×3 | |
  | 10~12 | 3×4 | |
  | 13~16 | 4×4 | 최대 권장 밀도 |
  | 17~50 | 5×N 자동 | 밀도 경고 표시(가독성 저하) |

  규칙: `cols = ceil(sqrt(N))` 기본, 위 표로 상한 보정. 50장 전체 인쇄는 허용하되 "장당 크기 축소" 안내.

- 인쇄 CSS: `@page { size: A4; margin: 8mm; }`, 갤러리 컨테이너 `display:grid; grid-template-columns: repeat(var(--cols),1fr); gap:4mm;`. 헤더에 고객명·채촌일·버전 캡션(선택).
- 이미지 소스는 인증이 필요한 `/api/v1/files/:id`(`files.controller.ts:29`) — 인쇄 페이지도 인증 컨텍스트 내에서 렌더하므로 axios가 아닌 `<img>` 직접 로드 시 토큰 전달 방식 확인 필요(현행 다운로드는 Bearer 인증). → §7 미결(이미지 인증 로딩 방식).
