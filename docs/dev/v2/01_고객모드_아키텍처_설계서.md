## 1. 배경과 문제 정의

plan_v2는 매장 태블릿에서 **직원이 고객을 옆에 두고** 조작하는 "고객 모드" 흐름(고객 등록 → 계약 → 스타일 컨설팅 → 서명 → 엑셀 → 채촌)을 요구한다. 현행은 단일 관리자 CRM으로 **모드 개념이 전무**하다.

| # | 현상 | 근거 |
|---|---|---|
| P1 | 화면 모드 구분이 없다. 메뉴는 권한(canSeeAdmin) 기반 노출만 있고, "관리자용/고객 대면용" 전환이 없다 | `frontend/src/app/AppLayout.tsx:40-82` (`canSeeAdmin`, `menuItems`), 공용 `frontend/src/shared/Can.tsx` |
| P2 | 모든 화면이 **전체 고객 리스트·금액·내부 정보**를 그대로 노출한다. 태블릿을 고객에게 보여주면 타 고객 정보가 함께 보인다 | 고객 목록 `customers.service.ts:57-162` (전체 목록 + `balanceAmount` 요약 `:134`) |
| P3 | 라우팅이 단일 트리다. `/login` 공개 + `/` 하위 전체가 `AuthGuard`→`AppLayout` 한 벌로 렌더된다. 대면용 축약 화면을 끼울 자리가 없다 | `frontend/src/app/router.tsx:40-101` |
| P4 | 흐름이 화면마다 끊긴다. "계약 완료 후 스타일 컨설팅으로" 같은 **단계별 next 이동**과 선택 고객 컨텍스트 유지 장치가 없다 | 각 feature 페이지가 독립 라우트(`router.tsx:59-74`)로만 연결 |
| P5 | 관리자/고객 대면 상태를 나눌 재인증 수단이 없다. 로그인만 있고 "현재 사용자 비밀번호 재확인" 엔드포인트가 없다 | `auth.controller.ts` (login/me/refresh/logout 4개뿐) |

**개편 목표**: 동일 관리자 로그인을 유지한 채 **UI 모드만 전환**한다(D1). 고객 모드는 검색해 선택한 **고객 1명**의 정보만, 4개 메뉴(고객·계약관리·스타일 컨설팅·채촌)로 대면 흐름을 제공한다. 관리자 복귀 시 **비밀번호 재인증**한다. 별도 고객 계정·저권한 세션은 만들지 않으며, 접근 제한은 **프런트 모드 상태 + 화면 컨텍스트**로 구현한다(백엔드 API는 기존 것을 재사용).

### 1.1 확정 정책 (D1 재확인)

| 항목 | 결정 |
|---|---|
| 로그인 | **동일 관리자 계정 유지.** 모드는 UI 레이어 상태일 뿐 세션·토큰과 무관 |
| 모드 전환 위치 | 좌측 메뉴 **최하단 [모드 전환] 버튼** |
| 고객 모드 진입 | 비밀번호 **불필요** |
| 관리자 복귀 | 비밀번호 **재입력(재인증)** 필수 |
| 고객 모드 메뉴 | **4개**: 고객 · 계약 관리 · 스타일 컨설팅 · 채촌 |
| 데이터 범위 | 검색해 선택한 **1명**만. 타 고객 리스트·결제성 금액 비노출 |
| 세션 모델 | 별도 고객 계정 없음. 프런트 모드 상태 + 화면 컨텍스트로 제한 |

## 2. 모드 상태 모델

### 2.1 전역 상태 (zustand 신규 스토어)

모드와 선택 고객을 담는 **신규 스토어** `frontend/src/app/mode-store.ts`를 둔다. 인증 스토어(`auth-store.ts`)와 분리해, 모드는 세션과 독립임을 코드로 드러낸다.

```ts
// frontend/src/app/mode-store.ts (신규)
export type AppMode = 'ADMIN' | 'CUSTOMER';

interface SelectedCustomer {
  id: string;
  name: string;
  phone: string; // 화면 표시는 마스킹 (§7)
}

interface ModeState {
  mode: AppMode;                       // 기본 ADMIN
  selectedCustomer: SelectedCustomer | null;
  enterCustomerMode: () => void;       // 비번 불필요, mode=CUSTOMER, selected 초기화
  exitToAdmin: () => void;             // 재인증 성공 후에만 호출, mode=ADMIN, selected=null
  selectCustomer: (c: SelectedCustomer) => void;
  clearSelectedCustomer: () => void;   // 검색 화면 복귀·유휴 타임아웃 시
}
```

**저장 위치와 영속성**: `auth-store`는 `persist({ name: 'aicrm-auth' })`로 localStorage에 남지만(`auth-store.ts:20-33`), **mode-store는 persist하지 않는다(인메모리)**. 근거:

- 새로고침·탭 재오픈 시 **항상 ADMIN**으로 복귀하고 `selectedCustomer`가 사라져야 안전하다(§7). localStorage에 남기면 태블릿을 방치·재로딩해도 직전 고객 컨텍스트가 되살아난다.
- 모드는 "지금 이 화면을 누구에게 보여주는가"라는 휘발성 UI 상태이지, 저장·복원 대상이 아니다.

### 2.2 새로고침 시 기본 모드 정책

| 상황 | 동작 | 근거 |
|---|---|---|
| 새로고침 / 재접속 | **ADMIN 기본**, `selectedCustomer = null` | mode-store 비영속. 로그인(accessToken)은 `auth-store` persist로 유지되므로 재로그인은 불필요 |
| 새로고침 후 관리자 진입 | **재인증 불필요** | 이미 로그인된 관리자의 페이지 재로드일 뿐. 재인증은 "고객 모드 → 관리자" 능동 전환에만 요구(D1) |
| 고객 모드에서 새로고침 | ADMIN으로 리셋 → 관리자가 다시 [모드 전환]으로 고객 모드 진입 | 대면 중 실수 리로드 시 고객 정보가 화면에 방치되지 않음 |

> 요약: **재인증은 "능동적 관리자 복귀" 액션에만** 건다. 새로고침 리셋은 재인증이 아니라 "안전한 초기 상태(ADMIN·고객 미선택)"로의 복귀다.

### 2.3 관리자 재인증 방식 — **권장: 신규 `POST /auth/verify-password`**

두 안을 비교한다.

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A (권장) | **`POST /auth/verify-password` 신규** — 현재 사용자 비밀번호만 검증, 토큰 무발급 | 세션 유지(D1 "동일 로그인"), refresh 회전 없음, 감사로그 명료, 잠금 카운터 재사용 | 엔드포인트 1개 추가 |
| B | 기존 `POST /auth/login` 재호출 | 신규 코드 없음 | **refresh token 회전(`auth.service.ts:63-96`)·재발급이 일어나 세션 상태가 흔들림**, loginId를 프런트가 다시 알아야 함, "재인증"이 아니라 "재로그인"이 됨 |

안 B는 login이 토큰을 새로 발급(`issueTokens` `auth.service.ts:83-96`)하므로 D1의 "동일 관리자 로그인 유지" 취지와 어긋난다. **안 A를 채택**한다. 상세 백엔드 설계는 §6.

## 3. 라우팅·레이아웃 설계

### 3.1 레이아웃 — **권장: 단일 `AppLayout` + 모드 조건부 메뉴**

별도 레이아웃 컴포넌트를 신설하지 않고, 현행 `AppLayout`이 `mode`에 따라 **메뉴·헤더·최하단 버튼만 분기**한다(D1 "UI만 전환"에 부합, 헤더·인증·코드라벨 하이드레이션 `AppLayout.tsx:37` 등 공통부 재사용).

```
                 mode = ADMIN                         mode = CUSTOMER
 ┌ Sider ──────────────────┐          ┌ Sider ──────────────────┐
 │ 대시보드 / 진행 현황 / 예약 │          │ 고객                      │
 │ 고객 / 계약 관리 / 컨설팅   │          │ 계약 관리                  │
 │ 채촌 / 제작 / 수선 / 결제…  │          │ 스타일 컨설팅              │
 │ (관리자: 기준정보·권한…)    │          │ 채촌                      │
 │ ──────────────────────  │          │ ──────────────────────  │
 │ [고객 모드로 전환] ← 최하단 │          │ [관리자 모드로 복귀]🔒 ← 재인증│
 └─────────────────────────┘          └─────────────────────────┘
```

- 현행 `menuItems`(`AppLayout.tsx:43-82`)는 `mode==='ADMIN'`일 때만 구성한다.
- `mode==='CUSTOMER'`이면 4개 항목만 구성하되, 각 링크는 선택 고객 컨텍스트 경로(§3.2)로 향한다. `selectedCustomer===null`이면 4개 메뉴는 비활성(검색 화면으로 유도).
- 최하단 [모드 전환] 버튼은 `menuItems`가 아니라 Sider 하단 고정 영역(`AppLayout.tsx:150` `</Menu>` 직후)에 별도 렌더한다.
  - ADMIN→CUSTOMER: 즉시 `enterCustomerMode()` 후 `/c`(검색) 이동. 비번 없음.
  - CUSTOMER→ADMIN: **재인증 모달**(§6.2) 오픈 → 성공 시 `exitToAdmin()` 후 `/`(대시보드) 이동.

### 3.2 고객 모드 컨텍스트 — **권장: URL 프리픽스 `/c/:customerId` + 전역 미러링**

선택 고객을 **URL(`/c/:customerId/*`)을 1차 진실로** 두고, `mode-store.selectedCustomer`가 표시·가드용으로 미러링한다. URL에 두는 이유: (1) 화면 간 next 이동(§4)에서 컨텍스트가 자연히 전파되고, (2) 딥링크·뒤로가기가 정상 동작하며, (3) "1명만"이 경로로 명시돼 가드가 단순하다.

신규 라우트 서브트리(`router.tsx`에 추가):

| 경로 | 화면 | 비고 |
|---|---|---|
| `/c` | 고객 검색 (default) | 검색 필드만. 선택 시 `/c/:customerId`로 |
| `/c/:customerId` | 진행상태 요약 홈 | 계약/컨설팅/채촌 진행상태 + 기본정보 + 이동 버튼 |
| `/c/:customerId/register` | 신규/예약 고객 등록 | 검색 결과 없음일 때. 예약정보 프리필 |
| `/c/:customerId/contract` | 계약 작성·최종확인·서명 | 03 화면을 고객모드 크롬으로 |
| `/c/:customerId/consulting` | 스타일 컨설팅 | 04 화면을 고객모드 크롬으로 |
| `/c/:customerId/measurement` | 채촌 | 05 화면을 고객모드 크롬으로 |

- 이 서브트리는 기존 `AuthGuard`→`AppLayout` 하위에 둔다(로그인 필요는 동일). `AppLayout`이 경로가 `/c`로 시작하면 자동으로 `mode==='CUSTOMER'` 렌더가 되도록, **경로↔모드 동기화 가드**(`CustomerModeGuard`)를 서브트리 element에 감싼다.
- `CustomerModeGuard`: 진입 시 `mode!=='CUSTOMER'`면 `enterCustomerMode()`, `:customerId`가 있으면 `selectCustomer` 동기화(없으면 상세 1건 조회로 채움). `:customerId`가 `selectedCustomer.id`와 불일치하면 URL 기준으로 갱신.
- **관리자 화면(계약/컨설팅/채촌 상세)은 재사용**하되, 고객모드에서는 라우트만 `/c/*`로 감싸 축약 크롬(상단 진행바 + 하단 next 버튼)을 입힌다. 화면 본체 컴포넌트는 공유하고, `mode`로 금액·리스트·부가버튼을 숨긴다(§5).

> 대안(단일 전역 `selectedCustomer`만, URL 프리픽스 없음)은 채택하지 않는다: 새로고침·딥링크에서 컨텍스트가 사라지고, 기존 `/contracts/:id` 등과 화면 공유 시 "지금 고객모드인지"를 매 화면이 스토어로만 판단해야 해 가드가 흩어진다.

## 4. 고객 모드 화면 흐름

전체 흐름(plan_v2): **고객 검색 → (없으면) 등록 → 계약 작성(비즈니스 구분·품목 수정) → 스타일 컨설팅 → 계약 최종확인(추가 옵션가) → 서명 → 엑셀 출력 → 채촌.** 각 화면 하단의 **단계 next 버튼**으로 `:customerId`를 유지한 채 이동한다.

```
 [/c 검색] ──검색──► 결과 있음 ─► [/c/:id 진행상태 요약]
                    │                    │
                    │              ┌─────┼───────────┬──────────┐
                    │           계약 작성   스타일컨설팅   채촌
                    └결과 없음─► [/c/:id/register]
                                (예약정보 프리필 or 최초등록) ─► 진행상태 요약

 계약 작성 ─[다음: 스타일 컨설팅]─► 컨설팅 ─[다음: 계약 최종확인]─►
   최종확인(옵션가 반영) ─[서명하기]─► 서명 ─[엑셀 출력]─► [다음: 채촌] ─► 채촌
```

### 4.1 검색 화면 (`/c`) — default

- **검색 필드만** 노출(고객명/전화). 목록을 미리 그리지 않는다(P2 대응). 기존 `GET /customers?q=`(`customers.controller.ts:17-21`) 재사용.
- 매칭 결과는 **선택용 최소 정보**(이름 + 마스킹 전화)만 카드로 표시하고, 금액·상태 배지는 숨긴다. 1건이면 자동 선택 제안, 여러 건이면 직원이 대면 확인해 1건 선택.
- 검색 결과 **없음** → [신규 고객 등록] 버튼 → `/c/:tempId/register`(또는 등록 후 실 id로 이동). 예약으로 생성된 PROSPECT가 전화로 존재하면 그 id로 등록 화면 프리필.

```
┌ 고객 모드 ─ 고객 검색 ───────────────────────────────┐
│                                                     │
│        고객명 또는 전화번호를 입력하세요                  │
│        ┌─────────────────────────────┐  [검색]      │
│        │                             │              │
│        └─────────────────────────────┘              │
│                                                     │
│   결과 ─────────────────────────────────────────    │
│   ┌ 정우성  010-****-9012 ┐  ← 선택                    │
│   └──────────────────────┘                          │
│                                    [+ 신규 고객 등록]  │
└─────────────────────────────────────────────────────┘
```

### 4.2 진행상태 요약 홈 (`/c/:customerId`)

- 선택 고객의 **기본정보 + 진행중 계약/컨설팅/채촌 진행상태 카드 3종**. 진행상태 값·게이팅은 **설계서 02**의 모델을 그대로 표시(cross-ref, 중복 설계 금지).
- 각 카드 클릭 = 해당 화면으로 이동. 결제성 금액(수금·미수·잔금)은 표시하지 않는다(§5, D6).

```
┌ 고객 모드 ─ 정우성 ─────────────────────  [관리자 모드로 복귀 🔒] ┐
```

## 5. 데이터 범위 제한

백엔드는 **기존 API를 그대로** 쓴다(신규 축약 API 없음). 노출 제한은 **프런트 모드·컨텍스트 필터**로 강제한다.

| 규칙 | 구현 |
|---|---|
| 목록/검색 1명 제한 | 고객모드는 `GET /customers` **목록을 화면에 그리지 않는다**. 검색(`?q=`)은 선택 목적의 최소 결과만 쓰고, 선택 후에는 `GET /customers/:id`(`customers.controller.ts:35-39`) **단건**만 사용. 계약·채촌 등 하위도 `?customerId=`/`:customerId` 고정 조회만 호출 |
| 타 고객 유입 차단 | `CustomerModeGuard`가 URL `:customerId`와 `selectedCustomer.id` 일치를 강제. 화면 내 "다른 고객으로" 류 링크·전체목록 버튼은 `mode==='CUSTOMER'`에서 렌더 안 함 |
| 결제성 금액 제외 (D6) | 고객모드에서 **수금·미수·잔금 등 결제성 금액 숨김**. 고객 목록 요약의 `balanceAmount`(`customers.service.ts:134`) 등 결제성 필드는 고객모드 화면에서 미표시 |
| 계약·옵션 가격은 표시 | 단, **계약 총액·품목/옵션 가격은 표시**한다(서명 전 가격 확인이 흐름의 목적 — plan_v2 "추가 옵션가격", D7 웹 표시규칙). 즉 "제외"는 결제성 금액이지 계약가격이 아니다 |
| 이중 방어 | 프런트 필터는 UX용. 백엔드 권한은 기존 `@RequirePermission('CUSTOMER_VIEW')` 등(`customers.controller.ts:18`)이 그대로 관리자 권한으로 검증한다(동일 로그인이므로 권한 동일). 고객모드는 권한 축소가 아니라 **표시 축소**임을 명확히 한다 |

> 주의: 고객모드는 관리자 권한을 그대로 쓰므로 "권한으로 막는" 게 아니라 "화면에서 안 보여주는" 방식이다. 민감정보 유출 방지는 §7의 컨텍스트 초기화가 핵심 방어선이다.

## 6. 관리자 재인증 백엔드 설계 (안 A)

### 6.1 엔드포인트

| 메서드 | 경로 | 권한 | 상태 |
|---|---|---|---|
| POST | `/auth/verify-password` | 로그인 필요(권한 데코 없음, `@Public` 아님) | **신규** |

- 요청: `{ "password": "..." }` (loginId 불필요 — 현재 토큰의 사용자로 검증)
- 응답: `{ "verified": true }` (성공) / 실패 시 `AUTH_INVALID_CREDENTIALS` 401
- `@Public()`을 붙이지 **않는다**. `@CurrentUser()`로 현재 사용자를 얻어 그 사용자의 비밀번호만 검증한다(`decorators.ts:11-20`).

```ts
// auth.controller.ts (추가)
@Post('verify-password')
@HttpCode(200)
verifyPassword(@CurrentUser() user: AuthUser, @Body() dto: VerifyPasswordDto) {
  return this.authService.verifyPassword(user.id, dto.password);
}
```

```ts
// auth.service.ts (추가) — login()의 bcrypt.compare(:37)·잠금(:39-45) 로직 재사용
async verifyPassword(userId: string, password: string) {
  const user = await this.prisma.user.findUnique({ where: { id: userId } });
  if (!user || user.status !== 'ACTIVE')
    throw new BusinessException('AUTH_INVALID_CREDENTIALS', '재인증에 실패했습니다.');
  const valid = await bcrypt.compare(password, user.passwordHash);
  if (!valid) {
    // login()과 동일한 loginFailures 카운터를 공유해 5회 실패 시 LOCKED (:9,:39-45)
    ...
    throw new BusinessException('AUTH_INVALID_CREDENTIALS', '비밀번호가 올바르지 않습니다.');
  }
  this.loginFailures.delete(user.loginId);
  return { verified: true };
}
```

- **토큰을 발급/회전하지 않는다.** 세션은 그대로 유지된다(D1).
- 실패 시 `login()`과 **동일한 `loginFailures` 카운터**(`auth.service.ts:9,:14`)를 공유해 5회 누적 시 계정 LOCKED. 재인증도 무차별 대입 대상이므로 동일 잠금 정책을 적용한다.
- 오류 코드는 기존 `AUTH_INVALID_CREDENTIALS`(`error-codes.ts:10`)를 재사용한다(신규 코드 불필요).

### 6.2 프런트 재인증 모달

- 신규 컴포넌트 `frontend/src/shared/ReauthModal.tsx`. [관리자 모드로 복귀] 클릭 시 오픈, 비밀번호 1필드.
- `POST /auth/verify-password` 성공 → `exitToAdmin()` → `/` 이동. 실패 → 인라인 오류, 잠금(401 `AUTH_ACCOUNT_LOCKED`) 시 로그아웃 유도.
- 취소 시 고객모드 유지.

### 6.3 감사로그

- 재인증 **성공/실패**를 감사로그로 남긴다. `AuditService.log({ userId, action: 'REAUTH', entityType: 'AUTH', entityId: userId, reason })` (구현표준 1.6). 비밀번호는 before/after에 포함하지 않는다(구현표준 1.6).
- 태블릿 공용 사용 특성상 "누가 언제 관리자 화면으로 복귀했는가"는 추적 가치가 높다.

## 7. 보안 고려 — 선택 고객 초기화 시점

태블릿 방치 시 고객모드가 **다른 고객 데이터를 유출하지 않도록**, `selectedCustomer`를 다음 시점에 반드시 초기화한다.

| 시점 | 처리 |
|---|---|
| 관리자 복귀(재인증 성공) | `exitToAdmin()` — `selectedCustomer=null`, `mode=ADMIN` |
| 로그아웃 | 기존 `clear()`(`AppLayout.tsx:115-123`)에 더해 mode-store도 리셋 |
| 새로고침·재접속 | mode-store 비영속(§2.1) → 자동으로 ADMIN·미선택 |
| 검색 화면(`/c`) 복귀 | `clearSelectedCustomer()` — 다음 고객 응대 전 컨텍스트 비움 |
| **유휴 타임아웃** | 고객모드에서 무조작 N분(기본 5분) 경과 시 `clearSelectedCustomer()` 후 `/c` 검색으로 자동 복귀. 관리자 화면(민감 전체정보)은 노출하지 않고 검색 화면으로만 되돌림 |

- 유휴 타이머는 `CustomerModeGuard` 레벨에서 관리(터치·키 입력 시 리셋).
- 재인증 모달이 열린 채 방치되면 일정 시간 후 자동 닫고 고객모드 유지(관리자 화면 노출 방지).
- 원칙: **고객모드의 기본 안전 상태 = "고객 미선택 검색 화면"**. 의심스러우면 이 상태로 되돌린다.

## 9. 테스트 항목

### 9.1 백엔드 (Jest)

- [ ] `verify-password`: 올바른 비밀번호 → `{verified:true}`
- [ ] 틀린 비밀번호 → 401 `AUTH_INVALID_CREDENTIALS`, 실패 카운터 증가
- [ ] 5회 연속 실패 → 계정 LOCKED(`login`과 카운터 공유 확인)
- [ ] 비로그인(토큰 없음) 호출 → 401(공용 가드), `@Public` 아님 확인
- [ ] 성공/실패 시 감사로그 `REAUTH` 기록, 비밀번호 미포함

### 9.2 프런트 (수동 인수, 태블릿)

- [ ] [모드 전환]으로 고객모드 진입 시 **비밀번호 없이** 전환, `/c` 검색만 노출
- [ ] 고객모드 메뉴가 4개(고객·계약·컨설팅·채촌)만 보임
- [ ] 고객 검색 → 1명 선택 후 그 고객 정보만 노출, **타 고객 리스트·결제성 금액 비노출**
- [ ] 검색 결과 없음 → 등록 화면, 예약 고객이면 프리필
- [ ] end-to-end: 고객 등록 → 계약 작성 → 컨설팅 → 최종확인(옵션가) → 서명 → 엑셀 → 채촌, 각 단계 next 버튼이 `:customerId` 유지
- [ ] [관리자 모드로 복귀] → 재인증 모달, 성공 시 관리자 메뉴 복귀 + `selectedCustomer` 초기화
- [ ] 재인증 취소 → 고객모드 유지
- [ ] 새로고침 → ADMIN·고객 미선택으로 복귀(재로그인 불필요)
- [ ] 고객모드 유휴 5분 → 검색 화면으로 자동 복귀, 컨텍스트 초기화
- [ ] 계약/옵션 가격은 표시되되 수금·미수·잔금은 숨김(D6 경계)
