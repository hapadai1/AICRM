## §1. 예약 30분 → 1시간 (A1)

### 1.1 현행 → 변경 요지
- **슬롯은 전적으로 프런트 표현**이다. 백엔드는 예약을 자유 timestamp(`scheduledStart`)로 저장하며 30분/1시간 슬롯 검증이 없다(`appointments.service.ts`에 slot/minuteStep 검증 없음 — 길이 제약은 관심품목 varchar(30)뿐 `:330-332`). 따라서 **A1은 프런트 전용 변경**이며 백엔드·스키마 변경이 없다(00 A1 확정과 일치).
- 요건: 시간단위를 1시간으로. "예약 고객만 출력(완료기능)"은 이미 존재하는 방문완료(VISITED) 흐름으로 충족되며(`appointment-constants.ts:18` `VISITED: 방문완료`), 캘린더/타임테이블은 예약 레코드만 출력한다(신규 요구 없음). 네이버 연동은 추후(현행 `SOURCE_META`/`SYNC_STATUS_META` 골격 유지).

### 1.2 화면 변경

## §2. 고객 필드 추가 (A2) + 상태 검색

### 2.1 현행 → 변경 요지
- Customer(`schema.prisma:173-200`)에 신체치수·나이 컬럼이 없다. 고객 상태는 `PROSPECT/CONTRACTED/INACTIVE` 3종(`customers.dto.ts:17`).
- 요건: **키·체중·나이**를 선택 입력으로 추가하고 고객상세·**작업지시서**에 표시. 검색은 전체상태(진행중/완료/전체) + 진행상태별 + 목록의 "고객상태" 열에 세부 진행상태 출력.
- **상태검색·세부 진행상태 열은 02(진행상태 재정의)의 journey `currentStage` 모델에 연계**한다. 본 문서는 신체 필드만 확정하고, 상태검색 UI/데이터는 **02를 단일 출처로 참조(중복 설계 금지)**한다. 현행 목록 열은 계약코드/거래유형 기준이며, 세부 진행상태 열 신설은 02의 단계 모델 확정 후 목록 응답(`CUSTOMER_SELECT`)에 journey 단계를 얹는다.

### 2.2 스키마 변경 (A2 확정: nullable·선택입력)
```prisma
// schema.prisma  model Customer (173-200) 에 3열 추가
model Customer {
  // ... 기존 필드 ...
  heightCm   Int?  @map("height_cm")   // 키(cm), 선택입력
  weightKg   Int?  @map("weight_kg")   // 체중(kg), 선택입력
  age        Int?  @map("age")         // 나이(세), 선택입력
  // ...
}
```
- 단위 표기를 컬럼명에 담아 혼선을 줄인다(`heightCm/weightKg`). 값 검증은 DTO에서 `@IsInt @Min(0)` + 상한(예: 키 300, 체중 500, 나이 150) 정도의 방어만.

### 2.5 작업지시서 연계 (→ 엑셀)
- 요건은 "키·체중·나이 → 엑셀 작업지시서"이다. `work-order-excel.ts`의 `WorkOrderExcelData`(43-66)는 현재 고객명/전화만 담는다. 고객 신체 3필드를 데이터에 추가하고, 정장 양식(송파) 상 여백/메모 칸 또는 신규 라벨 칸에 매핑한다.
  - 매핑 좌표는 채촌 신체열과 별개다. 05장(채촌 확장)의 신체열 매핑(`work-order-template-map.ts`)과 충돌하지 않도록 **고객 신체정보는 헤더/참고칸에 표시**하는 것을 기본으로 한다. 정확한 셀은 양식 확인 후 `work-order-template-map.ts`에 상수 추가.
- 구두 메모형 출력(§5-a)에도 동일하게 신체 3필드를 포함한다.

### 2.6 마이그레이션
- `20260726_v2_customer_body_fields`: `ALTER TABLE customers ADD COLUMN height_cm int, ADD COLUMN weight_kg int, ADD COLUMN age int;` — 전부 nullable이라 기존 데이터 무손상.

### 2.7 테스트 항목
- 고객 생성/수정/등록 시 3필드 저장·조회. 미입력 시 null 허용.
- 작업지시서 출력물에 신체 3필드 표기(육안). 채촌 신체열과 중복/충돌 없음.

### 2.8 미결사항 → **전건 확정 (2026-07-28)**
- 작업지시서 상 신체 3필드의 셀 좌표 — **확정**: 템플릿 실측으로 확정. 라벨 `키/몸무게`=`B3:I4` → 값칸 `J3:S4`(`CELL.bodySpec`), 라벨 `연령대`=`T3:X4` → 값칸 `Y3:AG4`(`CELL.ageGroup`). 출력 형식은 `178cm / 72.5kg`·`34세`이며 한쪽만 입력되면 있는 값만 적는다. 구두 간이시트에도 동일 출력. 채촌 신체열(`F`)과 겹치지 않는다.
- age는 **정수 직접입력 확정**(생년월일 파생 계산 도입하지 않음).
- 목록 "고객상태" 세부 진행상태 열의 값 집합·색상은 02의 단계 정의에 종속(cross-ref).

### 3.6-d 수선: 품목·개수 여러 줄 + 상태 5단계 + 고객 업무 처리 (2026-07-29)

**결정 1 — 접수는 품목을 여러 줄로 받는다.** 한 번 들어온 물건이 상의 1·하의 2처럼 섞이므로 단일 대상 품목으로는 못 적는다. `repair_request_items`(품목·개수·순번)로 옮기고 `repair_requests.target_product`는 제거한다. 순번은 화면 입력 순서이며, 수정(PATCH `items`)은 줄 단위가 아니라 통째 교체다. 맞춤 유형은 1줄 이상 필수, 일반 수선은 선택.

**결정 2 — 상태에서 '수선 중'(IN_PROGRESS)을 뺀다.** 접수 → 수선 요청 → 수선 입고 → 고객 연락 → 출고 완료 5단계. '수선 중'은 담당자가 따로 누를 일이 없는 껍데기였고, 업무 버튼 4개(수선요청 완료·입고 완료·고객요청·출고 완료)와 1:1로 맞으며 4단계 REPAIR 진행 트랙과도 어긋나지 않는다. 기존 '수선 중' 건은 '수선 요청'으로 이관하고, 이력의 '수선 중' 진입 이벤트는 지운 뒤 뒤 이벤트의 직전 상태를 '수선 요청'으로 잇는다.

**결정 3 — 수선 화면 하단에 '고객 업무 처리' 카드.** 고객을 고르면 그 고객의 수선 건을 전부 펼쳐 건마다 전체 단계·대상 품목을 보여 주고, 업무 버튼으로 한 단계씩 넘긴다. 지난 단계 버튼은 '완료'로 잠기고 지금 차례 하나만 눌린다(백엔드도 바로 다음 단계만 허용). 목록의 행 펼침 상태 변경은 그대로 둔다 — 하단 카드는 한 고객의 일을 몰아서 처리하는 자리다.

**마이그레이션** `20260729050000_v2_repair_items_and_status_flow`.

- 구현: `RentalAllocation`(`schema.prisma:855-879`)의 `pickupDate`(:859)·`availabilityEndDate`(:861)와 `status IN ACTIVE_ALLOCATION_STATUSES`(=RESERVED/CHECKED_OUT, `rentals.constants.ts`)로 일자별 점유를 산출. 기존 단일창 겹침 판정(`:543-549`, `pickupDate<=end AND availabilityEndDate>=pickup`)을 일 단위로 확장.
