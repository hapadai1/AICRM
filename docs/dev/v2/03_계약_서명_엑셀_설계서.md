### 1.2 목표

1. 계약 전체 작성 후 **[서명하기] 단계**에서 태블릿 손글씨 서명을 이미지로 캡처해 **계약 버전에 저장**한다.

## 2. 서명 스키마 · 저장

### 2.1 서명은 "계약 버전"에 붙인다

서명은 특정 시점 계약 내용에 대한 동의다. 계약은 버전 단위로 확정·변경(재계약)되므로(`ContractVersion.versionStatus` DRAFT→CONFIRMED→SUPERSEDED, `schema.prisma:371`), 서명도 **버전 단위**로 저장한다. 재계약(버전업) 시 새 버전은 서명 없는 DRAFT로 시작하고 **재서명**을 받는다(§2.5).

### 2.2 마이그레이션 (00 §4 집계 반영)

`contract_versions`에 서명 3개 컬럼 추가. FK는 표준(1.7)에 따라 RESTRICT. 신규·nullable이라 기존 데이터 무손상.

```prisma
model ContractVersion {
  // ... 기존 필드(schema.prisma:367-383) 유지 ...

  // --- v2 D4 전자서명 ---
  signatureFileId String?   @map("signature_file_id") @db.Uuid
  signedAt        DateTime? @map("signed_at") @db.Timestamptz(6)
  signerName      String?   @map("signer_name") @db.VarChar(80)

  signatureFile   File?     @relation("ContractVersionSignature", fields: [signatureFileId], references: [id])

  // ... 기존 relation 유지 ...
  @@unique([contractId, versionNo])
  @@map("contract_versions")
}
```

`File` 모델에는 역참조 relation을 추가한다(`schema.prisma:120` File):

```prisma
model File {
  // ...
  contractVersionSignatures ContractVersion[] @relation("ContractVersionSignature")
}
```

마이그레이션 파일명: `20260726_v2_contract_signature`(00 §4 `20260726_v2_*` 계열).

> **설계 판단 — EntityFile 대신 직접 FK를 쓰는 이유.** 서명은 버전당 **정확히 1개**이며 "서명 여부"를 확정 게이팅(§3.3)·엑셀(§5)·목록에서 자주 조회한다. `EntityFile`(다형 N:N, `schema.prisma:136`)로 두면 매번 `entityType='CONTRACT_VERSION', purpose='SIGNATURE'` 필터로 조인해야 하고 "1개뿐"을 스키마로 못 막는다. 직접 nullable FK가 존재 검사·include가 단순하다. 단, **이미지 바이트 자체는 `files` 모듈(File 레코드 + 스토리지)에 저장**해 파일 인프라(체크섬·다운로드·확장자 검증)를 그대로 재사용한다.

### 2.3 서명 이미지 저장 방식

프런트 캔버스가 만든 PNG를 **dataURL(`data:image/png;base64,...`)**로 서명 API에 보낸다. 서버는:

1. dataURL 헤더를 벗겨 base64 → `Buffer` 디코드, `image/png`만 허용.
2. `files` 모듈의 업로드 경로(`files.service.ts:50`)를 재사용해 `File` 레코드 + 스토리지 저장(`storageKey = YYYYMM/{uuid}.png`, sha256 체크섬).
   - `FilesController` 업로드는 multer `FileInterceptor`(`files.controller.ts` `POST /files`)라 파일 파트를 받는다. 서명은 dataURL(JSON body)이 태블릿에서 다루기 쉬우므로, `FilesService`에 **버퍼 직접 저장 헬퍼**(`saveBuffer({ buffer, mimeType, originalName }, actor)`)를 하나 추가해 계약 서비스가 내부 호출한다(multer 우회, 검증·감사·저장 로직은 공유).
3. 반환된 `fileId`를 해당 `ContractVersion.signatureFileId`에 기록하고 `signedAt`(서버 시각)·`signerName` 저장.

용량 가드: 디코드된 버퍼 상한(예: 2MB) 초과 시 `VALIDATION_ERROR`. 서명 캔버스 해상도를 감안하면 충분.

### 2.4 확정(계약완료)과 서명의 관계

- **서명은 확정의 전제조건**이다(D4). `confirm()`(`contracts.service.ts:401`)에서 확정 대상 DRAFT 버전의 `signatureFileId == null`이면 **`CONTRACT_SIGNATURE_REQUIRED`(409)**로 차단한다(§9 신규 에러코드).
- 순서: 전체 작성(초안 저장) → **[서명하기]로 서명 저장** → **[계약완료(확정)]**. 서명 API와 confirm은 별도 액션 엔드포인트(구현표준 1.1). 프런트가 서명 저장 성공 후 confirm을 호출한다.
- 서명 자체는 DRAFT 단계에서 저장되므로, 서명 후 확정 전에 내용을 고치면 서명이 무효가 될 수 있다 → §2.6 무효화 규칙.

### 2.5 재계약(버전업) 시 재서명 정책

- `createRevision()`(`contracts.service.ts:479`)은 현재 확정본을 복사한 새 DRAFT 버전을 만든다. **서명 컬럼은 복사하지 않는다**(새 버전 `signatureFileId=null`로 시작).
- `confirmRevision()`(`contracts.service.ts:546`)도 확정 대상 버전의 서명 존재를 동일하게 검사한다(§3.3). 즉 **재계약은 반드시 재서명**.
- 이전 버전의 서명은 그대로 보존된다(SUPERSEDED 버전에 붙은 채). 이력·감사 목적상 물리 삭제 금지(구현표준 1.7).

### 2.6 서명 후 내용 수정 시 무효화

- 서명이 있는 DRAFT 버전을 `update()`(`contracts.service.ts:352`)로 라인/금액 수정하면 서명 내용과 어긋난다. 이 경우 **해당 버전의 `signatureFileId/signedAt/signerName`을 함께 null로 되돌린다**(재서명 필요). 프런트는 "내용을 변경하면 서명이 초기화됩니다" 경고.
- 옵션 추가금액 반영(`applySurcharge`, `option-sessions.service.ts:535`)은 **현재 확정 버전의 금액을 제자리 수정**하며 버전을 올리지 않는다. 확정 후 발생하는 흐름이라 서명 무효화 대상이 아니다(계약서상 총액은 재출력 시 최신값 반영 — §5.4). 이 예외는 §11 미결로도 명시.

## 3. 서명 API

### 3.1 엔드포인트

액션 엔드포인트로 분리(구현표준 1.1). 컨트롤러 위치: `contracts.controller.ts`(신규 핸들러 추가).

| 메서드·경로 | 권한 | 설명 |
|---|---|---|
| `POST /contracts/:id/versions/:versionId/signature` | `CONTRACT_SIGN`(신규) | 서명 이미지 저장(생성/교체) |
| `DELETE /contracts/:id/versions/:versionId/signature` | `CONTRACT_SIGN` | 서명 제거(다시 받기용, DRAFT 한정) |
| `GET /contracts/:id/versions/:versionId/signature` | `CONTRACT_VIEW` | 서명 이미지 메타(dataURL 또는 downloadUrl) 조회 |

> `CONTRACT_SIGN` 권한 코드는 시드(부록 B 권한 시드)에 추가하고 서명 담당 역할에 부여한다.

### 3.2 요청·응답 DTO

`contracts.dto.ts`에 추가:

```ts
export class SaveSignatureDto {
  /** data:image/png;base64,... 형식 */
  @IsString()
  @Matches(/^data:image\/png;base64,/, { message: 'imageDataUrl은 PNG dataURL이어야 합니다.' })
  imageDataUrl: string;

  @IsString()
  @IsNotEmpty()
  @MaxLength(80)
  signerName: string;

  /** 낙관적 잠금: contracts.row_version */
  @IsOptional()
  @Type(() => Number)
  @IsInt()
  version?: number;
}
```

성공 응답(envelope `data`): `{ versionId, signatureFileId, signerName, signedAt, downloadUrl }`.

### 3.3 서비스 규칙 (`contracts.service.ts` 신규 `saveSignature`)

1. 계약·버전 조회. 버전이 이 계약 소속이 아니면 `NOT_FOUND`.
2. **DRAFT 버전만 서명 가능**. `versionStatus !== 'DRAFT'` → `CONTRACT_NOT_DRAFT`(확정본은 재계약으로만 수정). 기존 확정 로직과 동일 코드(`contracts.service.ts:354`) 정신.
3. `assertVersionMatch(contract.rowVersion, dto.version)`로 낙관적 잠금(`contracts.service.ts:901`).
4. `$transaction`(구현표준 1.5):
   - 기존 서명이 있으면 새 파일로 교체(직전 File은 참조 해제 후 미참조면 정리 대상 — 물리 삭제는 files 정책상 미참조 시에만, `files.service.ts:114`).
   - dataURL → 버퍼 → `FilesService.saveBuffer(...)`로 `File` 생성.
   - `ContractVersion.update`: `signatureFileId/signedAt(now)/signerName` 기록.
   - `AuditService.log({ action:'SIGN', entityType:'CONTRACT_VERSION', entityId: versionId, after:{ signerName, signedAt } })` — 트랜잭션 클라이언트로 호출(`asAuditClient`, `contracts.service.ts:986`).
5. **멱등**: 서명 저장은 재요청 시 최신 서명으로 덮어쓰는 것이 자연스러워 Idempotency-Key는 두지 않는다(확정처럼 부작용 누적이 없음). 필요 시 헤더 지원은 §11 미결.

### 3.4 확정 게이팅 반영

`confirm()`(`:401`)과 `confirmRevision()`(`:546`) 트랜잭션 초입, 대상 DRAFT 버전 조회 직후에 삽입:

```ts
if (!draft.signatureFileId)
  throw new BusinessException(
    'CONTRACT_SIGNATURE_REQUIRED',
    '서명이 완료되어야 계약을 확정할 수 있습니다.',
    [{ field: 'signature', reason: 'REQUIRED' }],
  );
```

## 4. 서명 화면 (태블릿)

### 4.1 캔버스 구현 — 자체 canvas 권장

| 방식 | 장단 |
|---|---|
| **자체 `<canvas>` + Pointer Events** (권장) | 의존성 0, 번들 경량, self-contained. 포인터 좌표를 선분으로 잇는 단순 로직이면 충분. `toDataURL('image/png')`로 캡처 |
| 외부 라이브러리(signature_pad 등) | 부드러운 곡선 보정은 낫지만 의존성 추가. 매장 태블릿 단일 환경엔 과함 |

권장: **자체 canvas**. 채촌 태블릿에서 `NumericKeypad`를 자체 구현한 선례(구현표준 2, v1 §2)와 일관. 고DPI 대응(`devicePixelRatio` 스케일), 펜 두께 고정, 배경 흰색(투명 PNG는 엑셀에서 안 보일 수 있어 흰 배경으로 캡처).

### 4.2 UX 흐름

계약 편집 화면에서 전체 작성·저장 완료 후 하단 **[서명하기]** 버튼 → 서명 단계(모달 또는 전용 라우트 `/contracts/:id/sign`).

```
[서명 캔버스 영역]  (터치/펜으로 서명)
서명자: [___________]  (기본값=고객명, 편집 가능)
[다시]  [취소]              [서명 저장]
                              ↓ 성공
계약 편집 화면 복귀 → [계약완료(확정)] 활성화
```

- **[다시]**: 캔버스 초기화(로컬만, 서버 미호출).
- **[서명 저장]**: `POST .../signature`. 성공 시 계약 화면의 "서명 완료" 배지(텍스트+색 병기, 구현표준 2) 표시, [계약완료] 활성화.
- **[계약완료]**: 서명 저장 뒤에만 활성. 미서명 상태에서 누르면 서버가 `CONTRACT_SIGNATURE_REQUIRED`로 막고 프런트도 사전 비활성.
- **미저장 이탈 경고**: 캔버스에 획이 있는데 저장 없이 벗어나면 경고(구현표준 2 "미저장 변경 시 이탈 경고").
- **재서명**: 이미 서명된 DRAFT를 다시 열면 기존 서명 미리보기 + [다시 서명] 제공.

### 4.3 라우팅·권한

- 고객 모드(설계서 01)의 4메뉴 중 "계약관리" 컨텍스트에서 검색한 고객 1명의 계약에 한해 서명 진행. 서명 버튼 노출은 `CONTRACT_SIGN` 권한(`<Can permission="CONTRACT_SIGN">`, 구현표준 2).

## 5. 계약서 엑셀 설계

### 5.1 생성 방식 — 양식 파일 없이 exceljs 코드 생성 권장

작업지시서(12장)는 **실물 공장 양식 xlsx에 값만 덮어쓰는** 방식이었다(병합·도식·인쇄영역이 고정 서식이라 코드로 다시 그리면 도식이 깨짐 — `work-order-excel.ts:14`, `preserveTemplateDrawings`). 계약서는 이와 다르다:

- **자체 표준 양식**을 새로 정의하는 것이라(D7) 지켜야 할 원본 xlsx·도식이 없다.
- 표 구조가 단순(헤더 + 품목표 + 총액 + 서명)해 코드 그리기가 자연스럽다.
- 서명 이미지를 셀에 앵커해 삽입해야 하는데, 이는 exceljs `worksheet.addImage`로 코드 생성 시 온전히 제어된다(템플릿 도식 보존 로직 불필요).

→ **결론: 가봉지시서와 같은 "코드로 워크북을 그리는" 방식**(`fitting-sheet-excel.ts` 계열)을 따른다. 작업지시서식 템플릿 덮어쓰기·`preserveTemplateDrawings`는 쓰지 않는다.

### 5.2 생성기 위치·시그니처

신규 파일 **`backend/src/modules/contracts/contract-excel.ts`**:

```ts
export interface ContractExcelLine {
  category: string;        // 대분류 라벨: 정장/셔츠/구두 (CATEGORY_LABEL, contracts.service.ts:28)
  components: string[];    // 세부 품목: JACKET/TROUSERS/VEST/SHIRT/SHOES 라벨 (COMPONENT_MAP, :22)
  quantity: number;
}
export interface ContractExcelOptionLine {
  optionName: string;      // 스타일 옵션명 (엑셀은 가격 제외)
}
export interface ContractExcelData {
  contractNo: string;
  status: string;
  contractedAt: Date | null;
```

### 5.4 파일 저장 vs 즉석 스트리밍 — 즉석 생성 권장

| 방식 | 성격 |
|---|---|
| 파일 저장형(작업지시서 `WorkOrderVersion`) | "출력=버전 생성"이라 산출물을 이력으로 보관해야 하는 문서에 적합 |
| **즉석 스트리밍형(가봉지시서, `production.controller.ts:90`)** (권장) | 요청 시 현재 계약버전 데이터로 그려 바로 내려줌. 저장 안 함 |

권장: **즉석 스트리밍**. 계약 내용·서명은 이미 `ContractVersion`에 버전으로 보존되므로 엑셀 파일 자체를 또 버전 저장할 필요가 없다. 서명(§2)과 옵션 추가금액(총액 제자리 수정, §2.6)이 반영된 **현재 시점 상태**를 항상 최신으로 출력하는 것이 옳다. 감사로그로 출력 사실만 남긴다(§8). (버전 스냅샷 파일 보관이 요건화되면 작업지시서식 파일저장형으로 승격 — §11 미결.)

## 6. 웹 화면 계약서 표시

D7 웹 규칙: **최초 = 품목·개수·가격 → 상세** / **스타일 옵션 추가 시 = 옵션명·가격 → 상세**. 즉 웹은 세부가격을 노출하고 "상세 토글"로 구성품·옵션을 펼친다.

### 6.1 상태별 표시

| 상태 | 요약 행(항상 보임) | 상세(토글) |
|---|---|---|
| 최초(옵션 미추가) | 품목(대분류) · 개수 · **가격(라인금액)** | 세부품목(구성품) 목록 |
| 스타일 옵션 추가 후 | 옵션명 · **가격(옵션 추가금액)** | 옵션 세부(부위·선택값) |

- 라인 가격은 `ContractLine.lineAmount`(`schema.prisma:403`, `contracts.dto.ts:49`).
- 옵션 추가금액은 `OptionSelectionValue.extraPriceSnapshot`(`schema.prisma:620`) 및 반영 상태(`applySurcharge`, `option-sessions.service.ts:535`)에서 가져온다.
- 데이터 소스: 확장된 `getDocument()`(§7) 또는 계약 상세(`getDetail`, `contracts.service.ts:336`) + 옵션 세션 조회. 상세 토글은 프런트 UI 상태.
- 배지·금액은 텍스트+색 병기(구현표준 2).

## 7. 엑셀 vs 웹 가격 표시 규칙

| 구분 | 품목 표시 | 가격 표시 | 근거 |
|---|---|---|---|
| **웹 화면** | 요약=품목/옵션명, 상세 토글로 세부품목·옵션 | **세부 가격 노출**(라인금액·옵션 추가금액) + 총액 | D7, plan_v2 "최초=품목 개수 가격>상세 / 옵션추가=옵션명 가격>상세" |
| **엑셀** | 대분류 + **세부품목 · 개수** | **세부가격 제외, 총액(총 계약금액)만** | D7, plan_v2 "엑셀=품목 세부품목/개수, 가격은 세부 제외 전체가격만" |

`getDocument()` 확장(§7.1)은 웹용으로 **세부가격 포함** JSON을, `buildContractExcel`(§5.2)은 **총액만** 받도록 데이터 소스에서 분리해 공급한다(엑셀 입력 `ContractExcelLine`에 가격 필드 자체를 두지 않는다).

### 7.1 `getDocument()` 확장(웹)

`contracts.service.ts:688`의 반환에 다음을 추가한다(웹 표시·상세 토글용):

- 각 라인의 `components`(세부품목 라벨·개수) — `COMPONENT_MAP`/`OrderItemComponent` 기준.
- `options[]`: 옵션명 + 추가금액(`extraPriceSnapshot`).
- **서명 상태**: `{ signed: boolean, signerName, signedAt, downloadUrl }`(엑셀 버튼·확정 버튼 게이팅용).

## 8. 엑셀 출력 API

| 메서드·경로 | 권한 | 응답 |
|---|---|---|
| `GET /contracts/:id/excel` | `CONTRACT_VIEW` | xlsx 스트리밍(attachment) |

컨트롤러(`contracts.controller.ts`)는 가봉지시서(`production.controller.ts:90`)와 동일하게 `@Res()`로 헤더 설정 후 `res.end(buffer)`:

```ts
res.setHeader('Content-Type',
  'application/vnd.openxmlformats-officedocument.spreadsheetml.sheet');
res.setHeader('Content-Length', String(buffer.length));
res.setHeader('Content-Disposition',
  `attachment; filename="${enc}"; filename*=UTF-8''${enc}`); // enc = contract-{contractNo}.xlsx
res.end(buffer);
```

서비스(`buildContractDocumentExcel(id, actor)`):
1. `getDetail`로 계약·현재버전·라인 로드(`contracts.service.ts:336`). 현재버전 없으면 `NOT_FOUND`.
2. 서명 로드: `currentVersion.signatureFileId`로 `File` 조회 → 스토리지에서 PNG 버퍼 읽기(미서명이면 서명 영역 공란 + "미서명" 표기, 단 확정 계약은 항상 서명 존재).
3. 옵션명·총액 등 `ContractExcelData` 구성 → `buildContractExcel(data)`.
4. **감사로그** `AuditService.log({ action:'EXPORT', entityType:'CONTRACT', entityId:id })` — 가봉지시서 출력 패턴(`production.service.ts:514`)과 동일.
5. `{ buffer, fileName }` 반환, 컨트롤러가 스트리밍.

프런트 다운로드는 인증 헤더가 필요하므로 `<a href>`가 아니라 axios blob 다운로드(작업지시서 `client.downloadFile()` 선례, 12장 §5).

## 11. 테스트 항목

**단위(Jest, 규칙 함수 우선 — 구현표준 4)**
- `buildContractExcel`: 품목표에 세부품목·개수만 나오고 **세부가격 미출력·총액만** 출력(D7). 서명 있음/없음 두 경우.
- dataURL 파서: PNG 헤더 검증, 비PNG·초과 용량 거부.
- 서명 무효화: 서명 있는 DRAFT `update` 시 서명 컬럼 null화.

**통합(테스트 DB — 핵심 트랜잭션)**
- 미서명 확정 → `CONTRACT_SIGNATURE_REQUIRED`(409). 서명 저장 후 확정 성공.
- 재계약 버전은 서명 미복사 → 재서명 없이 `confirmRevision` 실패, 재서명 후 성공.
- 낙관적 잠금: stale `version`으로 서명 저장 시 `CONTRACT_VERSION_CONFLICT`.
- 감사로그: `SIGN`(서명), `EXPORT`(엑셀 출력) 기록 확인.

**수동 인수(태블릿)**
- 서명 캔버스 그리기·[다시]·저장, 미저장 이탈 경고.
- 엑셀 다운로드 육안 확인 — 헤더·품목표·총액·서명 이미지(00 §5 S3 완료 기준 "서명 캡처·엑셀 다운로드 육안 확인").
