## 1. 배경 — 현행 대비 갭

### 1.1 맞춤(CUSTOM) 옵션 — 현행은 품목당 원단 단일 컬럼

- 옵션 선택은 **CUSTOM 전용 세션**이다. `OptionSelectionSession`은 `orderItemId` 단위이고 자유입력 원단은 **`fabricName` 단일 컬럼 하나뿐**이다: `backend/prisma/schema.prisma:584`.
- 구두는 이 단일 컬럼을 "컬러"로 재사용한다(프런트 라벨 오버라이드 `frontend/src/features/options/option-meta.ts:8-17`). **color/pattern 전용 컬럼은 없다.**
- 작업지시서 엑셀도 이 한 값을 상의·하의 원단 칸에 **동시에** 찍는다: `backend/src/modules/work-orders/work-order-excel.ts:314-315`(`upperFabricName`, `lowerFabricName` 둘 다 `data.fabricName`). 템플릿맵은 이 한계를 명시한다 — `work-order-template-map.ts:140` "원단이 자유입력 문자열(fabricName) 하나뿐 — 원단 마스터 없음".

> v2 요건(plan_v2): 정장1의 상의/하의/베스트 **각각** 원단·컬러·패턴을 수기입력하고, 정장2도 독립적으로 동일 입력한다. → 부위별 원단·컬러·패턴 저장 구조가 필요하다.

### 1.2 옵션세트 관리 — 세트가 SUIT 단위(부위 구분 없음)

- 옵션 마스터는 세트(`OptionSet.productCategory` @unique) → 버전(`OptionSetVersion` DRAFT/ACTIVE/RETIRED) → 단계(`OptionStage`) → 선택지(`OptionChoice` `imageFileId` 필수 + `extraPrice`) 구조다: `schema.prisma:499-575`.
- 정장 세트의 단계들(JACKET_BUTTON/LAPEL/POCKET/VENT/STITCH/LINING/TROUSER_* 등)은 **한 버전 안에 평면(flat)으로** 나열될 뿐, 어느 부위(상의/하의/베스트)에 속하는지 구분 컬럼이 없다.
- 버전업(수정=새 DRAFT 복사 → activate 시 기존 ACTIVE→RETIRED 단일 트랜잭션)은 **이미 구현**되어 있다: `option-master.service.ts:96`(createVersion), `:161`(saveStages, DRAFT만), `:217`(activate). → **재사용**한다(신규 아님).

> v2 요건(D5): 대분류 SUIT/SHIRT/SHOES 유지. 정장 세트 내부를 상의(JACKET)/하의(TROUSERS)/베스트(VEST) 부위 그룹으로 세분해 **그룹별로 이미지·옵션금액을 관리**. 셔츠/구두는 옵션금액 입력. 버전업 흐름은 현행 재사용.

### 1.3 렌탈 — 옵션 세션이 아님, 선택 흐름 자체가 없음

- 렌탈은 옵션세션과 무관하다. 재고는 `RentalSku`(componentType/design/color/size, `schema.prisma:813`) + `RentalInventoryItem`(관리코드 단위 실물, `:830`)이고, 배정은 `RentalAllocation`(`orderItemComponentId` + `rentalInventoryItemId` + 기간, `:855`)이다.
- 가용검색은 `rental-inventory.service.ts:523` `availability()` — componentType/design/color/size 필터 + 기간 미중복(EXCLUDE) + `availableFrom<=pickup`로 배정 가능 실물을 찾는다.
- 그러나 **"구성품별로 컬러·사이즈를 지정해 가용 실물을 골라 담는" 스타일 컨설팅 단계는 없다.** 현재는 재고관리자가 날짜를 정해 곧바로 배정하는 흐름뿐이다.

> v2 요건(D3): 렌탈 주문 품목의 구성품(상의/하의/베스트)별로 **컬러(12색 코드)·사이즈(코드)·비고(수선명령 수기)**를 지정 → 가용 렌탈 실물 검색·선택 → 배정으로 연계. 컬러 12색·사이즈는 기준정보 다운리스트 코드로 신규 구축.

### 1.4 기준정보 — resolve()가 2종뿐

- `admin-master.service.ts:39-56` `resolve()`는 `appointment-purposes`, `payment-method` **2종만** 지원한다(전용 테이블 위임, MasterRow = code/name/sortOrder/active).
- 코드성 고정 집합은 `admin-master/code-labels.constants.ts`(product-category, component-type, repair-type)에 있고 `master_code_labels` 오버라이드로 표시명만 바꾼다.

> v2 요건(D3): 렌탈 컬러 12색·사이즈 코드 신규 type을 `resolve()`에 추가.

## 2. 맞춤 옵션 확장 — 부위별 원단·컬러·패턴

### 2.1 핵심 결정: 부위별 **행/값** 저장 (컬럼셋 아님)

세션은 `orderItemId` 단위(품목당)인데 값은 부위(구성품)별로 필요하다. 두 안을 비교한다.

| 안 | 구조 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| A. 부위별 컬럼셋 | 세션에 `jacketFabric/jacketColor/jacketPattern/trouserFabric/…` 9컬럼 추가 | 조인 없음 | 부위 고정·확장 불가(베스트 없는 품목·셔츠/구두 낭비), 스키마 오염 | ✗ |
| **B. 부위별 행/값(권장)** | **신규 테이블 `OptionSelectionComponentAttr`** — (세션, 부위그룹)당 1행에 fabric/color/pattern | 부위 가변, D5 componentGroup과 정렬, 세션 복사 로직 그대로 확장 | 조인 1회 | **✅ 채택** |

**B안 채택 이유**: (1) 부위 구성이 품목마다 다르다(정장=상의/하의/베스트, 셔츠·구두=단일). (2) `OptionStage.componentGroup`(§3)와 동일한 부위 축을 공유해 화면이 부위 기준으로 일관되게 묶인다. (3) 세션 재편집·복사(§2.4)에서 값 복사 로직을 `values`와 동일 패턴으로 확장하면 된다.

### 2.2 신규 모델

```prisma
/// 맞춤 옵션 세션의 부위(구성품 그룹)별 원단·컬러·패턴 수기입력.
/// (세션, componentGroup)당 1행. 셔츠/구두는 componentGroup 단일 행.
model OptionSelectionComponentAttr {
  id                 String   @id @db.Uuid
  selectionSessionId String   @map("selection_session_id") @db.Uuid
  /// JACKET/TROUSERS/VEST/SHIRT/SHOES — component-type 코드 재사용(code-labels.constants)
  componentGroup     String   @map("component_group") @db.VarChar(20)
  fabricName         String?  @map("fabric_name") @db.VarChar(150)
  colorName          String?  @map("color_name") @db.VarChar(150)
  patternName        String?  @map("pattern_name") @db.VarChar(150)
  notes              String?  @map("notes")
  createdAt          DateTime @default(now()) @map("created_at") @db.Timestamptz(6)
  updatedAt          DateTime @updatedAt @map("updated_at") @db.Timestamptz(6)

  selectionSession OptionSelectionSession @relation(fields: [selectionSessionId], references: [id])

  @@unique([selectionSessionId, componentGroup])
  @@map("option_selection_component_attrs")
}
```

`OptionSelectionSession`에 역참조만 추가한다.

```prisma
model OptionSelectionSession {
  // ...기존 필드 유지...
  // fabricName은 하위호환용으로 남긴다(구두 컬러 재사용분 백필 원천). 신규 입력은 componentAttrs로.
  componentAttrs OptionSelectionComponentAttr[]
  // values / workOrderVersions 등 기존 relation 유지
}
```

> 하위호환: 기존 `fabricName`(`schema.prisma:584`)은 **삭제하지 않는다**(구현표준 §1.7 물리삭제 금지, 감사·작업지시서 히스토리 보존). 마이그레이션에서 각 CURRENT 세션의 `fabricName`을 대표 부위(정장=JACKET, 셔츠=SHIRT, 구두=SHOES) attr 행으로 백필한다(§8).

### 2.3 부위 세트 결정(어떤 부위 행을 만드나)

품목 카테고리 → 부위 그룹 목록. `contracts.service.ts:22-26`의 `COMPONENT_MAP`(SUIT→[JACKET,TROUSERS], VEST는 주문화면 추가)과 정합을 맞추되, **옵션 부위 세트는 별도 상수**로 고정한다(베스트 항상 포함).

```ts
// options/option-component-groups.ts (신규)
export const OPTION_COMPONENT_GROUPS: Record<string, string[]> = {
  SUIT:  ['JACKET', 'TROUSERS', 'VEST'],
  SHIRT: ['SHIRT'],
  SHOES: ['SHOES'],
};
```

세션 start 시 카테고리에 해당하는 부위 그룹 행을 **빈 값으로 미리 생성**하지 않고, 화면 입력 시 upsert한다(빈 행 남발 방지). detail 응답은 `OPTION_COMPONENT_GROUPS`로 부위 슬롯을 만들고 저장값을 채워 내려준다.

### 2.4 서비스 변경 (`option-sessions.service.ts`)

- **start(`:84`)**: `dto.fabric` 단일 갱신(`:95-100`)을 유지하되(하위호환), 신규 `componentAttrs` 배열 입력을 받아 부위별 upsert. 확정 세션 재편집 복사(`:146-194`)·copy(`:678`)에서 `values`를 복사하듯 `componentAttrs`도 함께 복사(부위별 fabric/color/pattern 이어받기).
- **신규 액션 `PUT /option-sessions/:id/component-attrs/:group`** — 부위별 원단·컬러·패턴·비고 upsert. `ensureEditable`(`:820`, CONFIRMED 불가) + `ensureVersion`(`:829` 낙관적 잠금) 재사용. 저장 시 세션 `lastSavedAt`·`rowVersion` 증가.
- **detail(`:295`)·review(`:471`)**: 응답에 `components: [{ componentGroup, fabricName, colorName, patternName, notes }]` 추가(부위 슬롯 = `OPTION_COMPONENT_GROUPS[category]`).
- **confirm(`:594`)**: 부위별 값은 필수 검증 대상이 아니다(자유입력·선택). 기존 단계(choice) 필수 검증만 유지. 부위 attr 요약을 감사로그 `after.componentAttrs`에 포함.

> 정장1/정장2 독립성은 **현행 그대로** 보장된다. 두 벌은 서로 다른 `OrderItem`(같은 category, 다른 `sequenceNo`, `schema.prisma:467` unique(orderId, productCategory, sequenceNo))이고 세션·부위 attr이 품목별로 분리된다. copy는 명시 요청 시에만.

### 2.5 작업지시서 엑셀 연동 (`work-order-excel.ts`)

현행은 `WorkOrderExcelData.fabricName`(`:50`) 한 값을 상·하의에 동시 출력(`:314-315`). v2는 부위별로 넓힌다.

```ts
// WorkOrderExcelData 확장 (하위호환: fabricName 유지)
components?: {
  JACKET?:   { fabricName?: string; colorName?: string; patternName?: string; notes?: string };
  TROUSERS?: { fabricName?: string; colorName?: string; patternName?: string; notes?: string };
  VEST?:     { fabricName?: string; colorName?: string; patternName?: string; notes?: string };
};
```

매핑(엑셀 양식 칸):

| 부위그룹 | 원단 → 칸 | 컬러·패턴 → 칸 |
|---|---|---|
| JACKET | `CELL.upperFabricName`(`:314`) | 상의 추가요청사항(컬러/패턴 병기) |
| TROUSERS | `CELL.lowerFabricName`(`:315`) | 하의 추가요청사항(컬러/패턴 병기) |
| VEST | 신규 칸 없으면 상의 추가요청사항에 "[베스트] 원단/컬러/패턴" 라인 추가 | 동일 |

`work-orders.service.ts`가 세션에서 데이터를 만들 때(`:211,372,593` 부근 `fabricName` 채우는 지점) `componentAttrs`를 조인해 위 구조로 전달한다. 대응 칸이 없으면 `applyOption`(`:194`)이 false 반환 시 추가요청사항으로 넘기는 현행 관례를 따른다.

## 3. 옵션세트 부위별 세분 (D5)

### 3.1 결정: `OptionStage`에 `componentGroup` 컬럼 추가

세트/버전 구조는 **바꾸지 않는다**(SUIT 세트 1개 유지). 정장 세트 내부의 각 단계에 소속 부위를 표시하는 컬럼만 추가한다. 그룹별 이미지·금액은 이미 **선택지 단위**(`OptionChoice.imageFileId` 필수 + `extraPrice`, `schema.prisma:561-565`)로 존재하므로, `componentGroup`은 이들을 **부위 탭으로 묶어 관리·표시**하는 축이 된다.

```prisma
model OptionStage {
  // ...기존 필드...
  /// JACKET/TROUSERS/VEST 등 부위 그룹. 셔츠·구두 등 단일 부위 세트는 null 허용.
  componentGroup String? @map("component_group") @db.VarChar(20)
  // 기존 @@unique([optionSetVersionId, stageCode]) / @@unique([optionSetVersionId, sequenceNo]) 유지
}
```

### 3.2 기존 정장 단계 → 부위 백필 규칙

stageCode 접두로 백필(마이그레이션, §8):

| componentGroup | 대상 stageCode(현행 `work-order-excel.ts:196-249` applyOption 케이스) |
|---|---|
| JACKET | JACKET_BUTTON, LAPEL, POCKET, VENT, SLEEVE_BUTTON, STITCH, LINING |
| TROUSERS | TROUSER_PLEAT, TROUSER_HEM, TROUSER_WAIST, TROUSER_* |
| VEST | VEST_* (신규 추가 단계 — 스티치·카라 등) |

셔츠·구두 세트 단계는 `componentGroup = null`(단일 부위).

**베스트 단계 반영(2026-07-27)** — `prisma/seed-suit-design-options.ts`(V1 제자리 갱신)에 2단계를 추가했다. 정장 세트는 그대로 1개, 내부만 상의 8 / 하의 3 / 베스트 2 = 13단계.

| stageCode | 단계명 | required | 선택지 |
|---|---|---|---|
| `VEST_STITCH` | 베스트 스티치 디자인 | **false** | 스티치(+22,000) / 스티치 없음 |
| `VEST_COLLAR` | 베스트 카라 디자인 | **false** | 노치드 카라 / 피크드 카라(+22,000) / 숄카라(+22,000) |

- **`required: false`인 이유**: `confirm()`(`option-sessions.service.ts:710`)은 미선택 **필수** 단계가 있으면 확정을 막는다. 베스트 단계를 필수로 두면 베스트가 없는 투피스 정장까지 전부 확정 불가가 된다. 프런트 확인서도 `missingCount`를 필수 기준으로 세도록 고쳤다(선택 단계 미선택은 안내만, 확정 버튼을 막지 않는다).
- **이미지**: 베스트 전용 촬영본이 없어 모양이 가장 가까운 자켓 사진을 빌려 쓴다(스티치←`STITCH_A/B`, 카라←`LAPEL_A/B/C`). `ChoiceSeed.imageFrom`으로 지정하며, `files` 레코드를 `originalName`으로 공유해 파일이 중복 생성되지 않는다. 베스트 사진을 받으면 `assets/suit-design/VEST_*.jpg`로 넣고 `imageFrom`만 지우면 된다.

### 3.3 마스터 서비스·검증 변경 (`option-master.service.ts`)

## 4. 렌탈 선택 흐름 신설 (D3)

### 4.1 결정: 신규 "렌탈 스타일 선택" 세션/라인 + 기존 배정 연계

| 안 | 접근 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| A. RentalAllocation 직접 사용 | 컨설팅 단계에서 곧바로 배정 | 테이블 신설 없음 | **배정은 픽업/가용종료 날짜 필수**(`schema.prisma:859-861`) + EXCLUDE 기간잠금. 컨설팅 시점엔 날짜 미정. 실물 선점이 이르다 | ✗ |
| **B. 렌탈 선택 세션/라인 신설(권장)** | 부위별 컬러·사이즈·비고·후보 실물을 담는 컨설팅 레이어. 날짜 확정(렌탈예약) 시 배정 생성 | 날짜 없이 스타일 확정, 확인서 출력, 배정과 분리 | 테이블 2개 신설 | **✅ 채택** |

**B안 채택 이유**: "무슨 컬러·사이즈의 어떤 실물을 원하는가"(스타일 컨설팅, 날짜 없음)와 "그 실물을 이 기간 예약한다"(RentalAllocation, EXCLUDE 기간잠금 `02_구현표준정의서.md:20-27`)는 생애주기가 다르다. 컨설팅에서 배정을 만들면 날짜 미정인데 실물을 선점하거나 날짜를 억지로 넣어야 한다.

### 4.2 신규 모델

```prisma
/// 렌탈 스타일 선택 세션 — 렌탈 주문 품목(OrderItem)당 1개(현재본).
/// 맞춤 옵션 세션과 분리된 렌탈 전용 흐름. transactionType=RENTAL 품목에만.
model RentalSelectionSession {
  id           String    @id @db.Uuid
  orderItemId  String    @map("order_item_id") @db.Uuid
  status       String    @default("IN_PROGRESS") @map("status") @db.VarChar(20) // IN_PROGRESS/CONFIRMED
  confirmedAt  DateTime? @map("confirmed_at") @db.Timestamptz(6)
  isCurrent    Boolean   @default(true) @map("is_current")
  rowVersion   Int       @default(0) @map("row_version")
  createdAt    DateTime  @default(now()) @map("created_at") @db.Timestamptz(6)
  updatedAt    DateTime  @updatedAt @map("updated_at") @db.Timestamptz(6)

  orderItem OrderItem              @relation(fields: [orderItemId], references: [id])
  lines     RentalSelectionLine[]

  @@index([orderItemId, isCurrent])
  @@map("rental_selection_sessions")
}

/// 부위(구성품)별 컬러·사이즈·비고 + 선택한 후보 실물/SKU.
model RentalSelectionLine {
  id                    String   @id @db.Uuid
  sessionId             String   @map("session_id") @db.Uuid
  /// 어느 구성품에 대한 선택인지 — OrderItemComponent와 연결(배정 대상 앵커)
  orderItemComponentId  String   @map("order_item_component_id") @db.Uuid
  componentType         String   @map("component_type") @db.VarChar(20) // JACKET/TROUSERS/VEST...
  /// 기준정보 rental_colors.code (12색)
  colorCode             String?  @map("color_code") @db.VarChar(30)
  /// 기준정보 rental_sizes.code
  sizeCode              String?  @map("size_code") @db.VarChar(30)
  /// 수선명령(수치 등) 수기 — 비고
  alterationNotes       String?  @map("alteration_notes")
  /// 선택한 후보 실물(가용검색 결과). 날짜 확정 전이라 nullable.
  selectedInventoryItemId String? @map("selected_inventory_item_id") @db.Uuid
  createdAt             DateTime @default(now()) @map("created_at") @db.Timestamptz(6)
  updatedAt            DateTime @updatedAt @map("updated_at") @db.Timestamptz(6)

  session               RentalSelectionSession @relation(fields: [sessionId], references: [id])
  orderItemComponent    OrderItemComponent     @relation(fields: [orderItemComponentId], references: [id])
  selectedInventoryItem RentalInventoryItem?   @relation(fields: [selectedInventoryItemId], references: [id])

  @@unique([sessionId, orderItemComponentId])
  @@map("rental_selection_lines")
}
```

`RentalInventoryItem`·`OrderItemComponent`에 역참조 relation을 추가한다(FK RESTRICT, 구현표준 §1.7).

### 4.3 흐름

1. 렌탈 주문 품목의 구성품 목록(`OrderItemComponent`, JACKET/TROUSERS/VEST) 조회.
2. 부위별로 **컬러(12색)·사이즈·비고** 지정(라인 upsert).
3. [가용 실물 검색] — 컬러/사이즈/componentType으로 `availability()`(`rental-inventory.service.ts:523`) 호출. **날짜 파라미터**: 컨설팅 단계 기본은 주문 `completionDueDate`/예상 사용기간(오더 필드) 또는 프런트 입력. 미지정 시 "기간 미확정" 모드로 상태·SKU 조건만 필터(availability는 날짜 필수이므로 §9 미결로 처리).
4. 후보 실물 선택 → `selectedInventoryItemId` 저장.
5. [확정] → `status=CONFIRMED`. 확인서 출력.
6. **배정 연계**(렌탈예약, 06장 A7 달력): 확정 라인의 `selectedInventoryItemId` + `orderItemComponentId`를 기본값으로 `RentalAllocation` 생성 화면에 넘긴다. 실제 기간잠금·EXCLUDE 검증은 배정 시점(`rental-allocations.service.ts`).
