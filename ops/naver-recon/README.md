# 네이버 예약 수집 — 운영 안내

CRM 은 네이버 예약을 **읽기만** 한다. 예약 확정·취소·수정은 코드에 없다 (네이버는 운영 데이터).

## 왜 스크래핑인가

네이버 예약은 개별 사업자가 신청해 쓸 수 있는 공개 API를 제공하지 않는다. 존재하는 연동은
승인된 솔루션 벤더와의 B2B 제휴뿐이고, 그마저 업종코드 제약이 있어 맞춤정장 업종은 대상이 아니다.
그래서 파트너센터 화면을 여는 방식으로 수집하되, 화면 HTML 을 긁지 않고 **화면이 스스로 호출하는
예약 목록 JSON 응답을 가로채** 쓴다 — 화면 개편에 덜 취약하고 파싱이 정확하다.

## 차단·캡차를 피하는 원칙

- **로그인을 최소로 한다.** 캡차가 터지는 지점은 거의 항상 로그인이다. 평소에는 저장된 세션
  (`.profile/`)을 재사용하므로 로그인이 아예 일어나지 않는다.
- **세션이 끊기면 자동 로그인 1회.** 사람 손을 빌리지 않고 스스로 복구한다. 값을 붙여넣지 않고
  한 글자씩 실제 키 입력으로 치며("로그인 상태 유지" 포함), 캡차·기기등록 같은 추가 확인이 뜨면
  **즉시 포기하고 사람에게 넘긴다** — 우회하지 않고 연달아 재시도하지도 않는다.
- **고정 주기를 쓰지 않는다.** 매 실행마다 `기본 간격 + 0~지터`를 새로 뽑아 시·분·초를 흩뜨린다
  (기본 180분 + 0~45분).
- **영업시간에만 돈다** (기본 10~20시). 새벽 무인 반복은 봇 신호이고, 그 시간 예약 변동도 사실상 없다.
- **실패 시 연타하지 않는다.** 연속 실패마다 간격을 2배씩(최대 8배) 늘려 물러난다.
- **파싱 검증은 네이버에 접속하지 않는다.** 저장된 캡처(`test/backend/fixtures/naver-bookings.sample.json`)로만
  테스트한다.

## 요청마다 스크래핑하지 않는다 — 수집본 파일

네이버 접속은 **주기 수집**과 **명시적 적재 명령**에서만 한다. 받은 결과는 원본·파싱 결과를 함께
`docs/naver-booking/` 에 저장하고, 나머지는 이 파일을 쓴다. (폴더는 `.gitignore` 등록 — 개인정보 포함)

| 파일 | 내용 |
|---|---|
| `latest.json` | 최신 수집본: 수집 시각·조회 기간·파싱 결과(`records`)·네이버 원본(`raw`) |
| `history/<시각>.json` | 과거 수집본 최근 30개 |

| 누가 | 네이버 접속 |
|---|---|
| 주기 수집 (3시간+랜덤) | 최근 30분 내 수집본이 기간을 덮으면 그것을 쓰고, 아니면 수집 |
| 예약 화면 "네이버 동기화" 버튼 | 위와 같음 — 여러 번 눌러도 30분에 최대 1회 |
| 충돌 해소 "네이버 채택" | **접속 안 함** — 수집본에서 찾는다 |
| `scripts/naver-check.ts` (점검) | **접속 안 함** — `--live` 를 붙였을 때만 수집 |
| `scripts/naver-sync.ts` (기간 적재) | 항상 수집 (명시적 명령) |

파일을 읽을 때는 원본을 다시 파싱한다. 파싱 규칙을 고쳐도 다시 수집할 필요가 없다.
최소 간격은 `NAVER_BOOKING_MIN_FETCH_INTERVAL_MIN`(기본 30분), 폴더는 `NAVER_BOOKING_DATA_DIR` 로 바꾼다.

## 수집본 점검하기 (네이버 접속 없음)

```bash
cd backend
npx ts-node scripts/naver-check.ts                 # 최신 수집본 요약
npx ts-node scripts/naver-check.ts --find=전재갑    # 특정 고객·예약번호가 수집본에 있는지
npx ts-node scripts/naver-check.ts --all           # 전체 목록
```

"이 예약이 왜 안 보이지?"는 먼저 이걸로 본다. 수집본에 없으면 수집 이후에 생긴 예약이고
(다음 수집 때 들어온다), 수집본에 있는데 CRM 에 없으면 적재 문제다(서버 로그의 `적재 실패` 확인).

`--live` 를 붙이면 네이버에 새로 접속해 수집본을 갱신한다. 세션이 끊겨 있으면 자동 로그인까지
시도하므로 **세션을 되살리는 용도**로도 쓴다. 창을 띄워 보려면 앞에 `NAVER_BOOKING_HEADLESS=false`.

## 기간을 지정해 CRM 에 적재하기

```bash
cd backend
npx ts-node scripts/naver-sync.ts --back=30 --ahead=30
```

주기 수집은 과거 7일~미래 45일만 본다(수집 공백이 길면 과거를 자동으로 더 본다, 상한 45일).
그보다 오래 멈춰 있었거나 과거 이력을 다시 채울 때 쓴다.
예약번호로 합쳐지므로 여러 번 돌려도 중복되지 않는다. 서버 로그의 `다음 네이버 예약 수집` 시각과
겹치지 않게 실행한다 (같은 크롬 프로필을 동시에 열 수 없다).

첫 적재(실수집 예약이 아직 없을 때)는 이 명령 없이도 자동으로 과거·미래 30일을 가져온다.

## 왜 "과거를 다시 보는 일수"가 핵심인가 (실측)

어떤 날짜의 예약은 **그 날 당일까지 계속 늘어난다.** 수집본 이력으로 측정한 충전율:

| 이용일까지 남은 일수 | 그 시점에 들어와 있는 비율 |
|---|---|
| 1일 전 | 60% |
| 2일 전 | 53% |
| 3~4일 전 | 32% |
| 5~7일 전 | 17% |

즉 **미래를 넓게 보는 것만으로는 그 날짜가 채워지지 않는다.** 그 날짜를 이용일 당일 또는
그 이후에 한 번 더 긁어야 비로소 채워진다. 그래서 과거 조회 일수(`LOOKBACK`)가
수집 공백보다 짧으면 그 사이 날짜는 **덜 찬 채로 영구히 굳는다.**

실제로 그런 일이 있었다: 서버가 2026-09-30 ~ 10-06 꺼져 있었고 당시 `LOOKBACK=2` 라
10-01~10-04 가 9/30 스냅샷(32~60% 수준)에 고정됐다. 2026-10-07 에 `--back=45` 로
백필해 25건을 되찾았다 (10-03 토요일은 4건 → 16건).

그래서 수집기는 **"마지막 수집 이후 지난 날수 + 마지막 수집일"** 만큼은 반드시 다시 본다
(`NAVER_BOOKING_MAX_LOOKBACK_DAYS`, 기본 45일 상한). 그보다 길게 멈췄으면 위 백필 명령을 쓴다.

## 목록 API 의 제약 (실측)

- **한 번에 31일까지만** 조회된다(`maxDays=31`). 넓은 기간은 30일 조각으로 나눠 조회한다.
- **50건씩 페이지**로 나눠 준다(`page`, `size=50`). 조각마다 마지막 페이지까지 넘긴다.
  (페이지 처리 전에는 61일치 172건 중 50건만 들어온 적이 있다)
- 추가 조회는 로그인된 화면 안에서 화면과 같은 주소·헤더로 보내고, 요청 사이 0.8~2.5초를 쉰다.

## 사람이 로그인해야 하는 경우

캡차·새 기기 등록·2단계 인증처럼 자동 로그인이 풀 수 없는 화면이 뜨면 수집이 멈추고
로그에 이유가 남는다. 그때만 아래로 사람이 한 번 로그인한다.

```bash
cd ops/naver-recon
npm install          # 최초 1회
node recon.mjs
```

크롬 창에서 직접 로그인하고(**"로그인 상태 유지" 체크**), 예약 목록이 보이면 터미널에서 Enter.
이후 자동 수집이 다시 무인으로 돈다.

## 정찰(캡처) 도구

`recon.mjs` 는 예약 목록 화면이 주고받는 JSON 을 전부 저장한다. 네이버가 화면·응답을 바꿔
파싱이 깨졌을 때 새 구조를 확인하는 용도다.

| 명령 | 용도 |
|---|---|
| `node recon.mjs --doctor` | 크롬·설정 점검만 하고 종료 |
| `node recon.mjs` | 창을 띄우고 사람이 탐색 → Enter 로 저장 |
| `node recon.mjs --auto` | 저장된 세션으로 목록만 열어 캡처 후 자동 종료 |

산출물은 `out/<타임스탬프>/` 에 쌓인다 (`summary.md` 가 엔드포인트 요약).
**`out/` 과 `.profile/` 은 예약 개인정보·세션 쿠키를 담으므로 커밋 금지** (.gitignore 등록됨).

## 설정 (저장소 루트 `.env`)

| 키 | 기본 | 뜻 |
|---|---|---|
| `NAVER_BOOKING_SYNC_ENABLED` | `false` | `true` 일 때만 실제 수집. 그 외에는 스텁이 붙는다 |
| `NAVER_BOOKING_BIZ_ID` | — | 예약 주소의 `/bizes/{ID}/` 값 |
| `NAVER_BOOKING_LOOKBACK_DAYS` | `7` | 과거 며칠까지 조회 — 덜 찬 날짜를 채우는 핵심 값 (위 "충전율" 참고) |
| `NAVER_BOOKING_LOOKAHEAD_DAYS` | `45` | 미래 며칠까지 조회 |
| `NAVER_BOOKING_MAX_LOOKBACK_DAYS` | `45` | 수집 공백을 메우려 과거를 늘릴 때의 상한 |
| `NAVER_BOOKING_SYNC_INTERVAL_MIN` | `180` | 기본 수집 간격(분) |
| `NAVER_BOOKING_SYNC_JITTER_MIN` | `45` | 간격에 더할 랜덤 폭(분) |
| `NAVER_BOOKING_SYNC_HOURS` | `10-20` | 수집할 영업시간대 (Asia/Seoul) |
| `NAVER_BOOKING_PROFILE_DIR` | `ops/naver-recon/.profile` | 로그인 세션이 든 크롬 프로필 |
| `NAVER_BOOKING_HEADLESS` | `true` | `false` 면 창을 띄워 동작 (문제 확인용) |
| `NAVER_BOOKING_MIN_FETCH_INTERVAL_MIN` | `30` | 이보다 최근 수집본이 있으면 네이버에 다시 접속하지 않는다 |
| `NAVER_BOOKING_DATA_DIR` | `docs/naver-booking` | 수집본 저장 폴더 (커밋 제외) |

**운영 전제**: 수집은 크롬이 설치돼 있고 로그인 프로필이 있는 머신에서 돈다.
세션 만료 시 사람이 창을 열어 로그인해야 하므로, 화면이 없는 서버에 올릴 때는
프로필을 만들어 옮기거나 그 머신에서 위 로그인 절차를 수행해야 한다.

## 수집 → CRM 반영 규칙

`AppointmentsService.syncNaverReservations` 가 반영한다.

- `source='NAVER'` + `externalId`(네이버 예약번호) 기준 upsert. 고객은 전화번호로 기존 고객에 연결하고,
  없으면 가망 고객을 만든다.
- 취소는 삭제하지 않고 `status='CANCELLED'` 로 반영
- **상태는 앞으로만 간다** (허용 전이 규칙). 직원이 CRM 에서 방문·노쇼·취소 처리한 예약을
  네이버에 "확정"으로 남아 있다는 이유로 되돌리지 않는다.
- CRM 에서 손댄 예약(`localOverride`)은 덮어쓰지 않는다. 네이버도 바뀌면 화면에 **충돌**로 뜬다.
- **바뀐 게 없으면 쓰지 않는다** — 행 버전·감사 로그가 주기 수집마다 불어나지 않고,
  직원이 열어 둔 수정 화면이 버전 충돌로 튕기지 않는다.
- **한 건이 실패해도 나머지는 적재한다.** 실패 건과 사유는 결과·로그에 남는다.
- 생성·변경·취소는 감사 로그에 남는다.

### 상태 매핑

| 네이버 | CRM |
|---|---|
| `RC02` 예약 신청(확정 대기) | `RESERVED` |
| `RC03` 예약 확정 | `CONFIRMED` |
| `RC04` 취소 | `CANCELLED` |
| `RC08` 이용 완료 | `VISITED` 방문완료 |

노쇼 코드는 실데이터에서 아직 못 봤다. 처음 보는 상태 코드는 그 예약만 건너뛰고 로그에 남긴다.

### 네이버 메뉴 구분

예약 목적은 CRM 공통 코드라 "예복상담"과 "정장상담"이 둘 다 **맞춤 상담**이 된다. 그래서 네이버 메뉴를
예약에 따로 보존하고(`naver_biz_item_id`/`naver_biz_item_name`), 예약 화면에서
**전체 / CRM / 네이버** 와 **네이버 메뉴별**로 나눠 본다.

- 구분 기준은 **메뉴 ID** 다. 메뉴 이름은 파트너센터에서 바뀐다 — 실제로 2026-09-17 오전
  `가봉_조율의 시간` → `가봉`, `비즈니스 맞춤정장_그 날을 입다.` → `정장상담` 으로 바뀌었다.
- 이름이 바뀌면 수집 때 같은 메뉴 ID 의 예전 예약에도 새 이름을 입힌다.
- **선택지의 기준은 파트너센터 상품 목록**이다. 적재된 예약에서만 메뉴를 뽑으면 예약이 0건인 상품이
  화면에서 사라진다 — 2026-09-18 에 `렌탈(정장대여)` 이 그렇게 빠졌다(예약 2건이 8/8·8/13 로
  수집 창 밖 과거였다). 그래서 예약 목록 화면이 함께 부르는 상품 목록(`/biz-items`) 응답을
  수집 때 같이 저장하고, 그것을 선택지로 쓴다. 예약이 없어도 선택지에 남고, 순서도 파트너센터
  설정(`order`)을 그대로 따른다.
- **선택지에 건수는 띄우지 않는다.** API 의 `count` 는 적재된 전체 누적(기간·상태 무관)이라
  화면의 기간을 바꿔도 변하지 않고, 적재 범위를 넓히면 커진다 — 해석 기준이 없어 오해를 준다.
  응답에는 필터 정확성 검증용으로 남겨 두고 화면에서만 뺐다.
- 상품 목록 응답을 못 잡은 수집에서는 **직전 저장본의 상품 목록을 유지**한다 (선택지가 사라지지 않게).
  파트너센터에서 삭제된 메뉴도 과거 예약이 남아 있으면 목록 뒤쪽에 이름순으로 붙는다.

### 목적 매핑

메뉴 이름이 바뀌어도 견디도록 **키워드 포함 여부**로 판정한다 (`naver-booking.mapper.ts` 의 `PURPOSE_RULES`).
이름이 `가봉_조율의 시간` → `가봉` 으로 바뀌었을 때도 그대로 맞았다.

| 메뉴 키워드 | CRM 목적 |
|---|---|
| `PICKUP` | `PICKUP` 완성복 출고 |
| `가봉` | `FITTING` 가봉 피팅 |
| `채촌` | `MEASUREMENT` 채촌 |
| `수선` | `REPAIR_RECEIPT` 수선 접수 |
| `렌탈`·`대여` | `RENTAL_CONSULTATION` 렌탈 상담 |
| `예복`·`상담`·`맞춤정장` | `INITIAL_CONSULTATION` 맞춤 상담 |

`대여` 를 따로 둔 이유: 렌탈 메뉴 이름이 `렌탈_필요한 하루` → `렌탈(정장대여)` 로 바뀐 적이 있어,
다음에 `정장대여` 만 남으면 `상담` 규칙에도 걸리지 않아 **조용히 맞춤 상담으로 새기** 때문이다
(예약이 버려지지 않으니 경고도 안 뜬다). 순서상 `가봉`·`수선` 이 위에 있어 `대여 가봉` 은 가봉으로 간다.

규칙에 없는 새 메뉴가 생겨도 **예약을 버리지 않는다** — 기본 목적으로 넣고 로그에
`목적 매핑 규칙에 없는 네이버 메뉴` 경고를 남기니, 그때 규칙을 보완하면 된다.

### 과거 예약이 비어 있을 때

주기 수집 창은 과거 7일~미래 45일(공백이 길면 최대 45일까지 자동 확장)이다. 연동을 켜기 전 예약이나
그보다 오래된 예약은 그 창에 영원히 걸리지 않으므로, 기간을 지정해 한 번 채워 넣는다
(예약번호로 합쳐지니 여러 번 돌려도 중복되지 않는다).

```bash
cd backend && npx ts-node scripts/naver-sync.ts --back=60 --ahead=45
```

적재 없이 "네이버엔 있는데 시스템엔 왜 없나"만 확인할 때는 `scripts/naver-check.ts` 를 쓴다
(`--live` 없이는 저장본만 읽어 네이버에 접속하지 않는다).

## 알아 둘 네이버 동작

- **일정 변경 = 새 예약 발급.** 네이버는 기존 예약을 취소(RC04)하고 새 예약번호를 만들며
  `previousBookingId` 로 잇는다. CRM 에는 취소된 예약과 새 예약이 각각 남고(이력 보존),
  새 예약 메모에 `[일정변경] 이전 예약번호 …` 가 붙는다.
- **예약 일시는 `snapshotJson` 에만 있다.** 상위 `startDate`/`endDate` 는 날짜까지만 준다.
